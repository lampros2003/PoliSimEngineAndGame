## 1. Democracy 3 / Democracy 4: how the simulation works internally

### Takeaway
Democracy 3 (2013) is a small, hand-authored, data-driven directed graph: about 220 nodes (40 simulation values, ~123 policies, 36 situations, 21 voter groups) joined by about 1,150 one-variable equations, every value normalised to 0–1 and clamped, stepped once per turn, with 2,000 simulated voters (the Democracy 4 figure) reading the result. Real-world units (currency, GDP, population) are a thin per-country presentation layer on top of the normalised graph, and treasury, debt and the interest rate live in hard-coded engine code outside the moddable data. Democracy 4 (Early Access 2020, 1.0 in 2022) keeps the same CSV graph format and C++ in-house engine and adds parties, coalitions, voting systems, emergency powers, media and corruption around it.

### Cited Findings

**Scale of the shipped Democracy 3 model (third-party count from the shipped CSVs, v1.34)**
- A 2026 reverse-engineering project that parses the game's own `data/simulation/*.csv` reports "~40 simulation values, ~123 policies, 21 voter groups, and situations" and states the model is "data, not code". [FILE] — [democracy3-solver README](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/README.md)
- The same project counts "1,149 edges, 40 outcomes and 36 crises" (situations), identical for all six base countries, because one `data/simulation/` folder serves every country. [FILE] — [democracy3-solver findings.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/findings.md)
- Of the 1,149 edges, 1,022 (89%) are affine (straight-line) in their source value. The rest are 96 power curves (exponents from `x^0.4` to `x^11`) plus 18 constants, reading only 57 distinct source nodes; 13 edges multiply by a second node. [FILE] — [democracy3-solver layer2.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/layer2.md)
- Counts above are a third party's, not Positech's. The same repo says "~130" policies in one note and 123 in another, and does not say which DLC were installed. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- The official store text says each voter is a mixture of a subset of 21 voter groups. [SEARCH] — [Democracy 3 on Steam](https://store.steampowered.com/app/245470/Democracy_3/)

**File formats and node types**
- The main simulation files sit in the game's `data/simulation` folder; the official guide calls `policies.csv` the most interesting. Simulation values load from `simulation.csv`, where each line starting with `#` is a new value. [SEARCH] — [Positech Democracy 3 modding guide](https://www.positech.co.uk/democracy3/modding.html); [Modding simulation values](https://ftp.positech.co.uk/democracy3/modding_sim.html)
- Files are `#`-delimited pseudo-CSV: column 1 is a literal `#` marking a data row, descriptions are quoted, and rows are padded with empty columns. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- `simulation.csv` row (D3): `#, name, guiname, description, zone, def, min, max, emotion, icon, #, <inputs…>, #, <outputs…>`. Two `#` markers split effects *into* the node from effects it exerts on others. `emotion` is HIGHGOOD, HIGHBAD, UNKNOWN or HIDDEN. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- `policies.csv` row (D3): `#, name, guiname, slider, description, flags, introduce, cancel, raise, lower, department, mincost, maxcost, costmultiplier, implementation, minincome, maxincome, incomemultiplier, #Effects, <effects…>`. `introduce/cancel/raise/lower` are political-capital costs, `implementation` is turns to take effect, and flags include `UNCANCELLABLE` and `MULTIPLYINCOME`. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- `votertypes.csv` row (D3): `#, name, guiname, plural, image, overriden joins, default, percentage, desc, color, #, <influences…>`. `percentage` is the group's population share; `influences` are `OtherGroup, weight` cross-membership pairs. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- `situations.csv` row (D3): name, gui name, description, zone, icon, start text, stop text, positive flag, **start trigger**, **stop trigger**, then inputs, `#`, outputs. [FILE] — [democracy3-solver loader.py](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/src/d3solver/loader.py)
- Democracy 4 `policies.csv` header, from a real mod file: `name, slider, flags, opposites, introduce, cancel, raise, lower, department, prereqs, mincost, maxcost, costfunction, cost multiplier, implementation, minincome, maxincome, incomefunction, incomemultiplier, nationalisation GDP percentage`, then `#Effects` and quoted effect cells. New against D3: `opposites`, `prereqs`, `costfunction`, `incomefunction`, nationalisation share. [FILE] — [D4 Overhaul Expansion policies.csv](https://github.com/AdeptusFreemanicus/D4-Overhaul-Expansion/blob/HEAD/data/simulation/policies.csv)
- Democracy 4 `situations.csv` header: `prereqs, positive, start trigger, stop trigger, cost, costfunction, income, incomefunction`, then inputs, `#`, outputs. Situations can carry a budget cost or income. [FILE] — [D4 economics overhaul situations.csv](https://github.com/vartemiou-svg/democracy4-economics-overhaul/blob/HEAD/mod/data/simulation/situations.csv)
- `sliders.csv` defines slider types: `#,name,DISCRETE,<steps>` or `#,name,PERCENTAGE,<min>,<max>`. [FILE] — [D4 Overhaul Expansion sliders.csv](https://github.com/AdeptusFreemanicus/D4-Overhaul-Expansion/blob/HEAD/data/simulation/sliders.csv)
- Dilemmas are INI-style text files: `[dilemma] name`, an `[influences]` list that sets how likely it is to fire (`_default_`, `_random_,min,max`, and node equations such as `Stability,0.4-(0.6*x)`), and `[option0]`/`[option1]` blocks whose `OnImplement` calls `CreateGrudge(target, value, decay)`. [FILE] — [D4 economics overhaul dilemma file](https://github.com/vartemiou-svg/democracy4-economics-overhaul/blob/HEAD/mod/data/simulation/dilemmas/AusterityProtests.txt)
- Events use the same shape: `[config] Name, Texture, GUISound, OnImplement = CreateGrudge(_All_,0.1,0.70);` plus `[influences]`. [FILE] — [D4 Overhaul Expansion event file](https://github.com/AdeptusFreemanicus/D4-Overhaul-Expansion/blob/HEAD/data/simulation/events/AShootingStar.txt)
- Dilemma effects cannot use inertia, per the official guide. [SEARCH] — [Positech Democracy 3 modding guide](https://www.positech.co.uk/democracy3/modding.html)
- Per-country edits are "override" INI files: `[override] TargetName = "Religious"`, `HostName = "Gambling"`, `Equation = "DELETE"`, `Inertia = 0`. An override replaces or deletes one edge. [FILE] — [Democracy 3 Taiwan mod override](https://github.com/audreyt/democracy3-taiwan-mod/blob/HEAD/Taiwan/data/missions/taiwan/overrides/gambling.ini)
- Base-game Democracy 3 uses overrides per country: USA deletes `HandgunLaws → ViolentCrimeRate`; France has six; Canada and Australia none. [FILE] — [democracy3-solver findings.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/findings.md)

**The link ("effect") equation syntax**
- Official layout of one effect cell: target, then value and operator terms, an optional further operator and value (rarely used), then an inertia figure. The guide recommends the free "graphcalc" program for seeing what an equation does. [SEARCH] — [Positech Democracy 3 modding guide](https://www.positech.co.uk/democracy3/modding.html)
- Observed grammar: each effect is `Target, formula [, inertia]`. `x` is the source node's current normalised value; operators are `+ - * /`, `^` (power) and parentheses. Examples from the shipped data: `-0.2+(0.4*x)`, `0.98*(x^4)`, `0.30*(x^0.6)+0.07`, `0.25*(x^5)*Narcotics`. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- A bare identifier other than `x` multiplies by another node's value. In the shipped D3 data only `*CarUsage` and `*Narcotics` appear, so nearly every link is a function of one variable. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- **Inertia** is an optional integer third field. Per the manual (p. 6, as cited by the solver project) the influence uses the moving average of the source value over that many turns; absent or 0 means instant. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- Real D4 effect cells with inertia: `"ShortTermYield,0.1-(0.35*x),2"`, `"Inflation,0.04-(0.12*x),6"`, `"GDP,-0.02+(0.06*x),8"`. [FILE] — [D4 economics overhaul policies.csv](https://github.com/vartemiou-svg/democracy4-economics-overhaul/blob/HEAD/mod/data/simulation/policies.csv)
- Cost and income multipliers are `;`-separated `Factor,formula` lists, e.g. `GDP,0.5+(0.5*x);TaxEvasion,1.0-(0.2*x)`. A `_default_,k` term is an additive base, the others multiply. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md); [findings.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/findings.md)
- Reserved node names: `_All_` (every voter group), `_default_`, `_LowIncome` / `_MiddleIncome` / `_HighIncome` (income by band), `_global_socialism`, `_global_liberalism`, `_globaleconomy_` (exogenous world cycle), `_year`, `_security_`, `_Terrorism`, and per-group `<group>_freq` (membership frequency) and `<group>_income`. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- Democracy 4 adds more reserved targets seen in mod files: `_effectivedebt_`, `_percept_strength` (a perception value), `_prereq_*` country flags (e.g. `_prereq_sovereign_currency`), `_random_`. [FILE] — [D4 Overhaul Expansion policies.csv](https://github.com/AdeptusFreemanicus/D4-Overhaul-Expansion/blob/HEAD/data/simulation/policies.csv); [D4 economics overhaul simulation.csv](https://github.com/vartemiou-svg/democracy4-economics-overhaul/blob/HEAD/mod/data/simulation/simulation.csv)

**Normalisation, combination rule and situations**
- Combination rule, confirmed against a v1.34 US save by single-step consistency check: `node_value = clamp(default + Σ influence_i, min, max)`. The default is a constant term, not just a starting value (mean absolute error 0.11 for that hypothesis against 0.34 for "sum only"). [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md)
- The equilibrium "runs entirely in the normalised [0,1] space the CSVs define — no absolute quantity enters it". Population, GDP range, income bands and `wealth_mod` are needed only by the budget layer, to turn slider positions into dollars. [FILE] — [democracy3-solver findings.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/findings.md)
- A situation is a node with its own value plus start and stop triggers (typically 0.6 and 0.4). It switches on above the start trigger and off below the lower stop trigger (hysteresis), and its output effects apply only while active. [FILE] — [democracy3-solver grammar.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/grammar.md); [solver.py](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/src/d3solver/solver.py)
- Treasury and national debt are "engine-accumulated, not CSV nodes"; consequences surface through the `DebtCrisis` situation and credit-rating events. [FILE] — [democracy3-solver scope.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/scope.md)
- 31 of 32 enacted US policies agree on one CSV-to-dollar conversion constant within ±11% (median 0.0265), i.e. policy costs in the CSV are abstract units scaled per country. [FILE] — [democracy3-solver findings.md](https://github.com/chrisaacson69/democracy3-solver/blob/HEAD/notes/findings.md)

### Inferences
- "Neural network" is a marketing term. Nothing in the data files is learned: every weight is a hand-typed equation, and `NEURON_NORMALIZATION_SCALAR` suggests "neuron" is simply the engine's class name for a node.
- The whole D3 simulation step is roughly 1,150 polynomial evaluations plus a few thousand voter updates per turn, once per player click. This is microseconds of work in any language. Democracy's engine has no performance problem to solve, so it offers no evidence that a custom high-performance engine is needed for this genre; its limits are in model design.
- Real units are cosmetic in Democracy. A game that wants people and currency as first-class quantities cannot reuse this architecture by rescaling: stocks (debt, population) and conservation (money spent equals money received) would have to become part of the graph, which they are not here.
- The moddable surface stops at data. Anything needing new logic (a bond market, a different interest formula) is impossible without engine source, as the save-patcher mod shows.
- Democracy 4 changed the political shell much more than the economic core. The CSV grammar is the same with a few extra columns.

### Gaps
- **Number of simulated voters in Democracy 3.** The 2,000 figure is stated for Democracy 4 only. The count is not in `simconfig.txt`, so it is probably hard-coded.
- **Exact turn-update order** (policies → simulation values → situations → voters → events/dilemmas) is not documented in anything I could reach. The solver project only proves the per-node combination rule.
- **Exact voting arithmetic.** The rule "happiness above 50% votes for the player" and the list of turnout factors are confirmed, but how membership strength, cynicism and complacency weight a voter's happiness, and the turnout formula, were not found. The constant names above show the ingredients.
- **Vanilla Democracy 4 node and link counts.** Only "120 events as of v1.27" was found. Mods only add rows, so mod files do not reveal base totals. Counting rows in an installed copy would settle it in minutes.
- **Democracy 3 implementation language** is, from memory, also C++ on Positech's own engine; one search specifically for this found nothing.
- **Turn length.** The Taiwan mission file sets `term_length = 16` for a four-year presidency, which implies quarterly turns; I recall this being the documented rule in both games but found no direct statement.
- Release dates from memory, unverified: Democracy 3 on 14 October 2013; Democracy 4 Early Access 6 October 2020, version 1.0 on 13 January 2022.
- The official modding-guide pages and the Democracy wiki could not be opened, so column meanings rest on a third party's reading of the shipped files plus real mod files.

## 2. Criticisms of the Democracy model, and what players asked for

### Takeaway
Reviewers criticised Democracy 3 for baking in a worldview (every actor is rational, and one policy graph applies to every country), for having almost no political opposition outside elections, and for being solvable. A 2026 data-level analysis adds harder evidence: values pinned at their clamps hide information, the budget sits outside the causal graph, and the shipped data contains typos that the engine silently tolerates.

### Cited Findings

### Inferences
- The strongest critique for our design is structural: with everything normalised and clamped, the model cannot say "how many people" or "how much money", and saturated values make further policy changes look inert. That directly supports the project's wish for real units, and equally shows real units need a stock-and-flow model.
- "Easy late game" follows from the structure: once key values sit at their clamps in the virtuous basin, nothing pushes back. A design with real stocks, budget constraints and opposition agency would not saturate the same way.
- Hand-typed equation strings with no validator produced errors even in the shipped game. A typed, validated data format with load-time checks is cheap and worth far more than raw engine speed.
- Bias is unavoidable in any authored causal graph; Positech's answer was transparency and overrides. Exposing equations and letting scenarios patch them is the low-cost mitigation.

### Gaps
- No academic essay labelling the game "neoliberal" was found; that framing is common in discussion but I could not source it.
- No Rock Paper Shotgun review turned up in the search; the "too easy" point rests on PC Gamer, Pocket Gamer, The Reticule and forum threads.
- "Opaque equations" as a criticism was not found in any review. The complaints found are about realism and difficulty. (From memory, unverified: the interface draws each link and its current strength on hover, so opacity is less of an issue than in most sims.)
- Steam and Positech forum wish-lists (requests for a legislature, local government, trade, demographics by age, real budgets) could not be opened.

## 3. Victoria 3 (and Victoria 2): pops, economy, performance, engine

### Takeaway
Victoria 3 (2022) simulates the world's population as grouped "pops" on a four-ticks-per-day clock, and its cost is driven by the *number of pop objects*, which grows through the game as migration and job changes split pops. Paradox's documented fixes are merging small pops and reducing splits, while a former Paradox tech lead states that Victoria 3's planned task-graph multithreading "didn't work. At all", so only one tick task runs at a time with parallel loops inside it.

### Cited Findings

**Tick structure and where the time goes**
- A tick is six hours, a quarter of a day; work is divided into yearly, monthly, weekly, daily and regular ticks. [SEARCH] — [Victoria 3 Dev Diary #76 – Performance](https://forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-76-performance.1570277/)
- "Victoria 3 splits each in-game day in 4 ticks." [FILE] — [Mathieu Ropert, "What makes a game tick? Part 5" (June 2025)](https://mropert.github.io/2025/06/17/making_games_tick_part5)
- The most expensive tick task is the employment update, followed by the pop-need cache update and the modifier update. [SEARCH] — [Victoria 3 Dev Diary #76](https://forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-76-performance.1570277/)
- "Especially in late game you could end up with large amounts of tiny pops which would make the employment update extremely slow." Version 1.2 (2023) made the game merge small pops more aggressively; a separate change gained about 4%. [SEARCH] — [Victoria 3 Dev Diary #76](https://forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-76-performance.1570277/)
- Early-2022 gains came largely from parallelising the modifier-node calculations. [SEARCH] — [Victoria 3 Dev Diary #76](https://forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-76-performance.1570277/)
- Migration used to split pops, raising pop counts and worsening performance as the game went on. The 1.6 rework (2024) cut the number of pops by about 15–20% towards the end game in internal tests. [SEARCH] — [Victoria 3 Dev Diary #105 – Migration in 1.6](https://forum.paradoxplaza.com/forum/threads/victoria-3-dev-diary-105-migration-in-1-6.1624226/)
- Paradox counts "Pops" as the number of different unique pops in a building, a state or the whole game, i.e. distinct groups, not people. Migration "works by regularly splitting Pops up and moving the pieces all over the place". [SEARCH] — [Victoria 3 Dev Diary #105](https://forum.paradoxplaza.com/forum/threads/victoria-3-dev-diary-105-migration-in-1-6.1624226/page-6)
- Already six weeks after launch, patch 1.0.6 (2022) reduced mid- and late-game pop counts by merging very small pops back into the general population. [SEARCH] — [Victoria 3 update 1.0.6 patch notes (GameWatcher)](https://www.gamewatcher.com/victoria-3-update-1-0-6-patch-notes)
- Dev Diary #76 also describes a heuristic cost system in which tick tasks declare how expensive each part of an update is. [SEARCH] — [Victoria 3 Dev Diary #76](https://www.paradoxinteractive.com/games/victoria-3/news/dev-diary-76-performance)
- In the 2024 retrospective diary the team says improved performance had been a stated goal of an update; the excerpt suggests the result fell short, without naming the update. [SEARCH] — [Victoria 3 Dev Diary #142 – 2024 in retrospect](https://admin-forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-142-2024-in-retrospect.1726056/page-2)
- A recent Paradox forum thread is titled "Has the attempt to improve computing power failed". [SEARCH] — [Paradox forum thread](https://admin-forum.paradoxplaza.com/forum/threads/has-the-attempt-to-improve-computing-power-failed.1832136)
- Markets: prices come from the balance of buy orders and sell orders around a base price; each country has a national market unless it is a subject sharing its overlord's; a state's orders are scaled by its market access. [SEARCH] — [Victoria 3 Dev Diary #9 – National Markets](https://forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-9-national-markets.1484917/page-3); [TheGamer market guide](https://www.thegamer.com/victoria-3-market-management-import-export-convoys-tariffs/)
- The 2025 trade rework added a World Market where autonomous trade happens; it is not where pops and buildings buy and sell goods. [SEARCH] — [Victoria 3 Dev Diary #143 – Trade rework: the World Market](https://admin-forum.paradoxplaza.com/forum/developer-diary/victoria-3-dev-diary-143-trade-rework-the-world-market.1733205)
- Player benchmark (a user, not a developer): a 1900 save took about twice as long per unit of game time as an 1840 save (2:14 against 1:03). [SEARCH] — [Paradox forum benchmark thread](https://admin-forum.paradoxplaza.com/forum/threads/victoria-3-performance-benchmark.1587827/page-12)
- Players still report late-game slowdowns of "maybe 3s/day" and worse. [SEARCH] — [Steam discussion: Late Game Performance](https://steamcommunity.com/app/529340/discussions/0/5350867208713926527/)

**Threading: statements from a former Paradox tech lead (Mathieu Ropert, Hearts of Iron IV tech lead, also worked on Victoria 3)**
- Original Europa Universalis-style ticks processed each country in turn, board-game style. The first parallel algorithms appeared "during a later Victoria 2 patch and/or during the development of Crusader Kings 2, in the very early 2010s". [FILE] — [Ropert, Part 6 (July 2025)](https://mropert.github.io/2025/07/15/making_games_tick_part6/)
- A 2010s tick in EU4 or HOI4 was `UpdateCountries(); UpdateProvinces(); UpdateArmies(); UpdateNavies(); UpdateAI();`, each split into a parallel pass and a serial pass. Parallelising was often "replacing a `for()` loop by a `parallel_for()` loop and see if anything exploded". [FILE] — [Ropert, Part 6](https://mropert.github.io/2025/07/15/making_games_tick_part6/)
- The root difficulty is "implicit data writes": games allow implicit read/write access to the whole game state, and can invoke script that does the same, so proving two functions race-free "becomes near impossible as the codebase grows". [FILE] — [Ropert, Part 6](https://mropert.github.io/2025/07/15/making_games_tick_part6/)
- Crusader Kings 3 formalised a two-phase pattern: a parallel `PreUpdate()` that reads anything but writes only to a per-object scratch buffer, then a serial `Update()` that applies results. Because the parallel phase changes no visible state it can run alongside rendering. [FILE] — [Ropert, Part 6](https://mropert.github.io/2025/07/15/making_games_tick_part6/)
- Victoria 3 defined the tick as a graph of system tasks (economy, construction, warfare…). "This is essentially the route that Victoria 3 went for. And sadly it didn't work. At all." The first implementation ran on one worker thread, and when more were enabled "the task graph was completely unreliable when it came to data races". [FILE] — [Ropert, Part 7 (October 2025)](https://mropert.github.io/2025/10/06/making_games_tick_part7/)
- Individual Victoria 3 tasks still use multiple threads through `parallel_for`-style loops; "the game just won't run 2 different tick tasks at the same time, unless it has been reworked since I left". [FILE] — [Ropert, Part 7](https://mropert.github.io/2025/10/06/making_games_tick_part7/)
- His proposed fix is data-driven parallelism: each task declares which collections it reads and writes, and the scheduler derives a race-free graph. He credits the idea to Bungie's 2015 "Multithreading the Entire Destiny Engine" talk. [FILE] — [Ropert, Part 7](https://mropert.github.io/2025/10/06/making_games_tick_part7/)
- He gave a public talk titled "Multi Threading Model in Paradox Games: Past, Present and Future". [FILE] — [Ropert, Part 6](https://mropert.github.io/2025/07/15/making_games_tick_part6/); [talk on YouTube](https://www.youtube.com/watch?v=M6rTceqNiNg)

**Engine and scripting (Clausewitz / Jomini)**
- Paradox Development Studio games run on the in-house Clausewitz engine; Ropert warns most public pages about it are "out of date, completely wrong, or both". [FILE] — [Ropert, Part 2 (April 2025)](https://mropert.github.io/2025/04/30/making_games_tick_part2/)
- Gameplay content is written in "PDS script", plain text files of triggers and effects that programmers inspect with a text search. Script is a recurring performance hazard because its author and the person who must fix it are in different disciplines. [FILE] — [Ropert, Part 3 (May 2025)](https://mropert.github.io/2025/05/07/making_games_tick_part3/)
- Hearts of Iron IV decisions now have six different trigger blocks, half of which exist only as performance hints that narrow what the script engine must evaluate. [FILE] — [Ropert, Part 4 (May 2025)](https://mropert.github.io/2025/05/27/making_games_tick_part4/)
- An early Victoria 3 frame-rate bug came from a city-graphics script binding that recalculated a state's pollution every frame, something the scripter had no means to fix. Soft rule at Paradox: name a method `Get` only if trivial, otherwise `Calc`. [FILE] — [Ropert, Part 5](https://mropert.github.io/2025/06/17/making_games_tick_part5)
- "Modifiers" are Paradox's name for the collections of bonuses and penalties applied to an object; they are a distinct, heavily accessed data set. [FILE] — [Ropert, Part 7](https://mropert.github.io/2025/10/06/making_games_tick_part7/)
- A Rust parser for the Clausewitz/Jomini text and binary formats covers EU4, EU5, CK3, HOI4, Victoria 3 and Imperator (MIT licence, 99 stars, active November 2026). [FILE] — [rakaly/jomini](https://github.com/rakaly/jomini)
- An F# library parses, edits and validates Paradox script files (MIT, 155 stars). [FILE] — [cwtools](https://github.com/cwtools/cwtools)

**Victoria 2 economy, as documented by its open-source reimplementation**
- Victoria 2's daily economic update iterates over nations in order of rank. [FILE] — [Project Alice economy design](https://github.com/schombert/Project-Alice/blob/main/docs/economy_design.md)
- Victoria 2 resolves the domestic-versus-world price problem by "ordering the consumers in an arbitrary fashion": each buys from domestic supply until it runs out, the rest pay the world price. Project Alice calls this "not great" because profitability then depends on position in an arbitrary order. [FILE] — [Project Alice economy design](https://github.com/schombert/Project-Alice/blob/main/docs/economy_design.md)
- "Even a close approximation requires substantial sequencing, and little parallelism is possible." Their aim is to store as little as possible and make as few passes over the data as possible. [FILE] — [Project Alice economy design](https://github.com/schombert/Project-Alice/blob/main/docs/economy_design.md)
- Each pop has one culture, one religion and one type, and stores how many of its people support each ideology and issue position; totals are aggregated to province, state and nation as floating-point arrays. [FILE] — [Project Alice demographics data](https://github.com/schombert/Project-Alice/blob/main/docs/demographics_data.md)

### Inferences
- The unit of cost in a pop simulation is the number of *groups*, not the number of people. Any design that splits groups along several attributes (job, culture, religion, place, employer) will see group counts grow during play unless merging is built in from day one.
- Victoria 3 shows that multithreading retrofitted onto a shared mutable world fails even with a large professional team. If parallelism matters, data access must be declared and enforced from the first line of code. This is the one place where the choice of language or engine genuinely matters, since Rust's ownership rules and ECS schedulers enforce exactly this.
- A market economy with ordered sequential clearing (Victoria 2) is inherently serial. Economic algorithms should be chosen for parallel friendliness (compute from last tick's prices, apply all at once) before any engine work.
- Script that can touch anything is both the reason these games are moddable and a leading source of performance and threading problems.
- A head-of-government game with one country and quarterly or monthly turns needs orders of magnitude less throughput than Victoria 3, which runs roughly 1,460 ticks per game year for the whole world.

### Gaps
- **Pop object counts** (at start and late game) and total simulated population: two searches found no official number.
- **Later performance diaries** (versions 1.5, 1.7, 1.8, 1.9 and 2025–26 patches): two searches found no dedicated diary. A forum comment says the 1.8 patch notes promise late-game improvements; not checked.
- **Date of Dev Diary #76.** One search summary dated it February 2022, which cannot be right for a game released in October 2022; from memory it accompanied patch 1.2 in early 2023. Its reference to "early 2022" gains is about pre-release development.
- **How pops, buildings and interest groups work in detail** could not be sourced. From memory, unverified: pops are keyed by profession, culture, religion, state and workplace; buildings turn input goods into outputs via production methods and pay wages and dividends; prices move within ±75% of a base price with no stockpiles; eight interest groups draw clout from pop wealth and votes; the main economic update is weekly. ## 5. Simulation-heavy games as performance references

### Takeaway
Developers of the largest simulations report the same three lessons: the big wins come from doing less work through better algorithms and data layout (Factorio's belts went from per-item to constant-time updates), naive multithreading can be slower than serial because threads fight over memory, and determinism plus multithreading is harder than either alone. Cities: Skylines II shows that adopting a modern multithreaded data-oriented stack did not prevent a failed launch, and SimCity (2013) shows the design cost of cutting agent state to save computation.

### Cited Findings

**Factorio (Wube Software)**
- Factorio's multiplayer uses deterministic lockstep: clients stay in step by running the same simulation rather than exchanging state. [SEARCH] — [Friday Facts #188 – Bug, Bug, Desync](https://factorio.com/blog/post/fff-188)
- A slow client cannot simply be ignored as in a client–server game, because ignoring it "would cause the game to break for everyone". [SEARCH] — [Friday Facts #76 – MP inside out](https://factorio.com/blog/post/fff-76)
- During development a fast, incomplete state check runs every tick to catch desyncs. [SEARCH] — [Friday Facts #55 – MP preview](https://factorio.com/blog/post/fff-55)
- Belt rework for version 0.15 (2017): item movement became an O(1) update, with gains of "x50-100" on item movement in isolation and an expected real-world gain of about 5–10 times; factories running at 25 updates per second rose to 35–40 from the belt change alone. [SEARCH] — [Friday Facts #176 – Belts optimization for 0.15](https://www.factorio.com/blog/post/fff-176)
- First multithreading attempt (3 November 2017, by kovarex and Klonan): threads kept invalidating each other's cache, so the parallel version ended up slower than the serial one; data from unrelated objects shared memory pages. The proposed remedy was per-chunk or per-task memory allocation so two tasks never work on the same memory. [SEARCH] — [Friday Facts #215 – Multithreading issues](https://factorio.com/blog/post/fff-215)
- 2024: a desync appeared only when the game ran on two computers with different numbers of CPU cores. Rseding's conclusion: "multithreading is hard, deterministic multithreading even more so". [SEARCH] — [Friday Facts #415 – Fix, Improve, Optimize](https://www.factorio.com/blog/post/fff-415)
- For version 2.0 the team looks for read-mostly work to parallelise, e.g. belt readers that pull data and emit one frame of signals without interfering with each other. [SEARCH] — [Friday Facts #421 – Optimizations 2.0](https://www.factorio.com/blog/post/fff-421)
- Mods "if written incorrectly can cause desyncs very easily". [SEARCH] — [Factorio forum: Desyncs and how to report them](https://forums.factorio.com/53851)

**Cities: Skylines II (Colossal Order / Paradox, October 2023)**

**General and open-source evidence**
- General framing from a Paradox veteran: simulation performance is under-discussed compared with graphics and asset streaming, and the common engine pattern of calling a virtual `tick()` on every object is the baseline to move away from. [FILE] — [Ropert, Part 1 (April 2025)](https://mropert.github.io/2025/04/23/making_games_tick_part1/)
- He regards C# in Unity as too powerful to count as a scripting language, and says script without guardrails gives non-programmers "unlimited power" to slow the tick. [FILE] — [Ropert, Part 3](https://mropert.github.io/2025/05/07/making_games_tick_part3/)
- Operating-system scheduler latency for waking worker threads can be in the hundreds of microseconds, which matters when a tick is split into many small parallel jobs. [FILE] — [Ropert, Part 9.5 (October 2026)](https://github.com/mropert/mropert.github.io/blob/HEAD/_posts/2026-10-20-making_games_tick_part9_5.md)
- Project Alice (C++ Victoria 2 remake): "most OOS [out-of-sync] bugs occur NOT due to floating points, but rather due to multithreading". [FILE] — [Project Alice devlog, February 2024](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2024-02/log_en.md)
- Project Alice re-implemented `sin`, `cos` and `acos` itself because the standard library versions differ by platform, and in debug builds computes a checksum every tick to locate desyncs. [FILE] — [Project Alice multiplayer technical notes](https://github.com/schombert/Project-Alice/blob/main/docs/multiplayer_technical.md)
- Project Alice stores game state in a generated structure-of-arrays "data container" with SIMD support (SSE3, SSE4.2, AVX2); early builds required an AVX2 CPU. [FILE] — [Project Alice devlog, February 2024](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2024-02/log_en.md); [September 2023 devlog](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2023-09/log_en.md)
- OpenVic's simulation library bans floating point in simulation code and uses a 64-bit fixed-point type with 48 integer bits and 16 fractional bits, because float results "vary with compiler, optimization flags, FMA contraction, and x87-vs-SSE". [FILE] — [OpenVic-Simulation determinism.md](https://github.com/OpenVicProject/OpenVic-Simulation/blob/master/docs/ecs/determinism.md); [FixedPoint.hpp](https://github.com/OpenVicProject/OpenVic-Simulation/blob/master/src/openvic-simulation/core/object/FixedPoint.hpp)
- OpenVic requires results to be bit-identical "regardless of CPU, worker-thread count, or whether the session was freshly started or loaded from a save", and provides parallel sum/min/max helpers that fold per-chunk results in a fixed order so the answer does not depend on thread timing. [FILE] — [OpenVic-Simulation determinism.md](https://github.com/OpenVicProject/OpenVic-Simulation/blob/master/docs/ecs/determinism.md)

### Inferences
- None of these developers credits its programming language for its performance. Factorio's gains are algorithmic (constant-time belts) and memory-layout driven; its first threading attempt made things slower. A custom engine earns its keep only if the team will actually do this kind of data-layout work, which needs a profiled, working simulation first.
- Cities: Skylines II is the cautionary case for technology-first thinking: a modern multithreaded stack, a 30-updates-per-second design target, and still a missed benchmark, a player base split on whether the simulation is fast enough, and the studio losing the franchise two years later.
- SimCity shows the opposite failure: cutting persistent agent state to save computation produced behaviour players read as fake. For a political game, simulating fewer, statistically weighted groups honestly is safer than simulating many shallow agents.
- Scale needed here is small by these standards. Factorio and RimWorld run 60 simulation steps per second; a head-of-government game needs one step per player turn, or at most a few per in-game day, so three to five orders of magnitude more time is available per step.
- Determinism (needed for lockstep multiplayer, replays and reproducible bug reports) is lost through thread ordering more often than through floating point. A design that fixes the order in which parallel results are combined gets determinism and parallelism together.
- Fixed-point arithmetic suits a real-units economy well: currency should be an integer type anyway, and it removes cross-platform drift.
- Structure-of-arrays storage with generated accessors (Project Alice) or an archetype ECS (OpenVic) are the two proven layouts for pop-style simulations; both exist as open-source C++ that can be studied.

From memory, unverified: the engine is custom C++ at a fixed 60 updates per second with Lua for data and mods; further posts worth opening are #204, #209 and #271 (cache and fluid optimisation) and #147, #149 and #302 (multiplayer).

## 6. Open-source political and economic simulation games and engines

### Takeaway
Two active open-source C++ reimplementations of Victoria 2 exist and are directly instructive: OpenVic (MIT licence, Godot front end over a separate headless simulation library with its own deterministic ECS) and Project Alice (GPL-3.0, playable, custom data container). There is no mature open-source Democracy-style game; the nearest assets are a 2026 Python re-implementation of Democracy 3's equilibrium and mature open-source tax-and-benefit microsimulation engines that already work in real currency units.

### Cited Findings

**Victoria 2 remakes**
- OpenVic: main repo MIT-licensed, 482 stars, created January 2023, pushed 13 November 2026; requires Godot 4.7.2, CMake 3.28+ and Ninja; game logic is a C++ GDExtension. [FILE] — [OpenVic README](https://github.com/OpenVicProject/OpenVic); a third-party index earlier listed it as GPL-3.0 [SEARCH] — [ecosyste.ms listing](https://awesome.ecosyste.ms/projects/github.com%2FOpenVicProject%2FOpenVic), which conflicts with the LICENSE file I read (MIT).
- OpenVic-Simulation is a separate C++ library (MIT, created May 2023, pushed 11 November 2026, about 67,000 lines in 381 source files) that builds as a static library, a headless executable, unit tests and optional benchmarks. [FILE] — [OpenVic-Simulation README](https://github.com/OpenVicProject/OpenVic-Simulation)
- It contains its own archetype-and-chunk entity-component system with documented rules: structural changes go through a command buffer applied at stage barriers, every component type must be checksummable (enforced at compile time), and threaded systems get per-chunk buffers. [FILE] — [OpenVic-Simulation ECS docs](https://github.com/OpenVicProject/OpenVic-Simulation/tree/master/docs/ecs)
- A third-party index still describes OpenVic as "Unplayable" with development active. [SEARCH] — [osgameclones Victoria II entry](https://osgameclones.com/victoria-ii)
- Project Alice: C++, GPL-3.0, 566 stars, created January 2023, pushed 8 November 2026; a continuation of the author's earlier Open V2; has shipped releases up to v1.2.x and runs inside a Victoria 2 install using its assets. [FILE] — [Project Alice README](https://github.com/schombert/Project-Alice)
- Its lead deliberately avoided design changes until feature-complete, because improving things as he went was "a major reason that [Open V2] got sidetracked and ultimately abandoned". [FILE] — [Project Alice about.md](https://github.com/schombert/Project-Alice/blob/main/docs/about.md)
- Architecture: the game loop runs on its own thread at all times; the UI never calls it directly but writes commands that it picks up, and receives events through single-producer single-consumer queues. Commands have paired `can_…` validity functions. [FILE] — [Project Alice game loop basics](https://github.com/schombert/Project-Alice/blob/main/docs/game_loop_basics.md)
- Multiplayer is lockstep: every client runs the simulation, the server rebroadcasts commands and tells clients when to advance a tick. [FILE] — [Project Alice multiplayer technical notes](https://github.com/schombert/Project-Alice/blob/main/docs/multiplayer_technical.md)
- The first public alpha (0.8.7) came in November 2023, ten months after the repository was created. [FILE] — [Project Alice devlog, November 2023](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2023-11/log_en.md)

- Its storage layer is a separate library, DataContainer (MPL-2.0). [FILE] — [schombert/DataContainer](https://github.com/schombert/DataContainer)
- Mods must be compiled into a "scenario file" before play; changing a mod invalidates old saves. [FILE] — [Project Alice devlog, September 2023](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2023-09/log_en.md)

[FILE] — [Project Alice devlog, January 2024](https://github.com/schombert/Project-Alice/blob/main/docs/Devlogs/2024-01/log_en.md)

### Inferences
- OpenVic-Simulation is the closest existing thing to "a custom high-performance engine for a pop-and-economy game": MIT-licensed, headless, deterministic, with an ECS, fixed-point maths and thread-count-invariant reductions. After nearly four years of volunteer work a third-party listing (possibly out of date) still marks the game on top as unplayable, and I saw no release mentioned in its README. That is a data point, though a soft one, on the cost of engine-first development.
- Project Alice reached a public alpha in ten months and has since shipped 1.x releases, by cloning an existing, fully specified design and refusing scope changes. Its lead's own account says changing the design while building the engine is what killed the predecessor.
- Both projects separate a headless simulation core from the presentation layer, which is the practical middle path: write the simulation as a library (in Rust or C++) and put an existing engine or UI toolkit in front of it.
- The microsimulation engines show a third architecture worth considering for a real-units fiscal game: vectorised rule evaluation over a representative sample of households, run in Python at interactive speeds. Their AGPL licences would constrain direct reuse in a commercial game.
- There is no open-source Democracy-like engine to build on, so the policy-graph layer would be new work either way; it is also the smallest part.

### Gaps
- No performance benchmarks (ticks per second, pop counts) were found for OpenVic or Project Alice.
- I did not find open-source national budget "games" (the repository search for that phrase returned nothing); public budget simulators run by think-tanks and newspapers exist but appear to be closed-source web tools.
- Citybound's actor-based architecture and its stated scale goals are from memory and not checked.
- GitHub star counts and dates were read from the GitHub search API on 13 November 2026.
