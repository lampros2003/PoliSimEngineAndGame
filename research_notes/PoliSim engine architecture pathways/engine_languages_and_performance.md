## 1. Language comparison for this workload, as of 2026 (Rust, C, C++, Zig; briefly Odin, Jai, Mojo, Julia)

### Takeaway
Rust (1.100.0, 12 Nov 2026) and C++ (C++23 in production, C++26 technically complete but tooling such as modules still rough) are the two options with a deep, current library ecosystem for exactly this workload; C (C23 default in GCC 15+) is viable and has strong existence proofs for deterministic multithreaded SIMD simulation (Box2D v3, flecs) but offers the least help with safety; Zig is still pre-1.0 (0.16.0, April 2026) with a large standard-library break in its latest release and lost its flagship user (Bun) to Rust in 2026. No option is ruled out on raw performance; the differentiators are safety, tooling, ecosystem churn and determinism controls.

### Inferences
- The dev.to "1.89 stabilised portable SIMD" claim is probably a confusion with stabilisation of AVX-512 intrinsics in `std::arch`; every primary source retrieved shows `std::simd` still feature-gated.
- For a library that must be embedded in a game client, called from Python and compiled to wasm, Rust has the most complete single-toolchain story today (cdylib/staticlib + cbindgen header, PyO3 0.29 + maturin wheels, wasm32 targets), with two soft spots: cbindgen is thinly maintained, and threaded wasm needs nightly + build-std. A C core gets the same reach via plain headers, ctypes/cffi and Emscripten with fewer moving parts but no safety net. C++ gets it via `extern "C"` shims and pybind11/nanobind (not researched here).
- Zig's risk profile for a multi-year project is the highest of the four: pre-1.0, a std-wide I/O API break in the most recent release, `@cImport` deprecated (C interop mechanics changing), small foundation, and LLM training data that lags the fast-moving std. Its C interop and cross-compilation remain genuine strengths (Uber uses it for cross-compilation), so "Zig as build tool for a C core" is a lower-risk use than "Zig as the engine language".
- LLM-assistance evidence is thin and mixed: small tests favour C/C++ slightly, Zig is consistently weakest, and Rust's compiler diagnostics make LLM repair loops effective at scale (Bun). No rigorous 2026 benchmark comparing these four languages was found.
- "Async irrelevance": nothing in the workload is I/O-bound; data parallelism (rayon/OpenMP/TBB-style) is the relevant model, so Rust async, C++ `std::execution` and Zig's new `std.Io` async are not selection criteria. (`std::execution` could serve as a task-graph substrate in C++26 but compiler/library availability was not verified.)

## 2. Evidence on Rust versus C/C++ for numerical and simulation code

### Takeaway
Measured evidence says idiomatic Rust lands within a few percent of C/C++ for this kind of code; the bounds-check tax is typically 0–8% and mostly matters when a check blocks autovectorisation, which is avoidable with iterators/slices. The honest costs are compile times, nightly-only portable SIMD and threaded wasm, and ergonomic friction for graph-shaped data (solved by index-based representations rather than pointers).

### Cited Findings
- Bounds checks: a research paper measuring checked indexing in a real application found 7.7% overhead with an older compiler, 6.5% with a newer one, 2.5% on a different architecture and 4.4% under a different workload — [NADER paper (Princeton)](https://www.cs.princeton.edu/~npopescu/papers/nader.pdf)
- ReadySet removed bounds checks from a hot path in a large production Rust codebase and found the difference was within noise to a few percent; the cost is real mainly when a check prevents optimisations such as autovectorisation — [ReadySet blog](https://readyset.io/blog/bounds-checks)
- Techniques for eliminating bounds checks without `unsafe` (iterators, slicing to a known length up front, `chunks_exact`, asserting lengths) are documented — [Shnatsel, "How to avoid bounds checks in Rust without unsafe"](https://shnatsel.medium.com/how-to-avoid-bounds-checks-in-rust-without-unsafe-f65e618b4c1e)
- Rust float semantics: RFC 3514 specifies that `+ - * / %`, `abs`, `copysign`, `mul_add`, `sqrt`, float casts and comparisons "exactly match IEEE 754-2008", and that strict IEEE guarantees preclude the compiler turning `a*b + c` into FMA; fast-math would need separate opt-in intrinsics/types — [RFC 3514](https://github.com/rust-lang/rfcs/blob/master/text/3514-float-semantics.md)
- Real projects: Rapier (Rust physics) offers optional cross-platform determinism and a `parallel` feature whose results match sequential regardless of thread count — [Rapier determinism docs (search summary)](https://rapier.rs/docs/user_guides/rust/determinism). Bevy shipped 0.19 on 19 June 2026 (261 contributors, 1,185 PRs) and 0.20 on 8 Oct 2026; still 0.x with roughly quarterly breaking releases — [Bevy 0.19](https://bevy.org/news/bevy-0-19/), [Bevy 0.20](https://bevy.org/news/bevy-0-20/). Polars is a Rust, Arrow-based, multi-threaded SIMD query engine — [pola-rs/polars](https://github.com/pola-rs/polars). Bun 1.4 (2026) is a production runtime ported from Zig to Rust — [InfoQ](https://www.infoq.com/news/2026/09/bun-ai-rewrite-zig-rust-4-months/)
- Rust ABM: krABMaga (MIT, crate 0.6.x, 228 stars, 494 commits) is a MASON-style discrete-event ABM engine; its intra-step `parallel` feature is labelled "Experimental" and the README publishes no benchmark figures — [krABMaga](https://github.com/krABMaga/krABMaga). An independent 2022 study (ISISLab, Applied Sciences) compared krABMaga with MASON, Agents.jl, Mesa, NetLogo and Repast on Flockers, Wolf-Sheep-Grass, Schelling and ForestFire at 1,000–128,000 agents on an i7-8700T; the repository README does not reproduce the numbers — [ABM_Comparison](https://github.com/isislab-unisa/ABM_Comparison)
- Honest downsides, documented: Polars' own distribution build has "extreme compile times" — [pola-rs/polars](https://github.com/pola-rs/polars); the parallel front-end is still nightly — [Cargo guide](https://doc.rust-lang.org/cargo/guide/build-performance.html); `std::simd` is nightly — [portable-simd](https://github.com/rust-lang/portable-simd); wasm threads need nightly — [wasm-bindgen-rayon](https://github.com/RReverser/wasm-bindgen-rayon); recent stable releases needed point releases for miscompilations (1.98.1 vtables; 1.99.1 FFI `bool` returns on x86_64) — [rust-lang/rust releases](https://github.com/rust-lang/rust/releases); a February 2026 benchmark found the Cranelift back-end only about 5% faster than LLVM for incremental builds of Zed, and only with debug info disabled — [cg_clif goal page](https://rust-lang.github.io/rust-project-goals/2026/improve-cg_clif-performance.html)

### Inferences
- For the two PoliSim workloads the expected Rust-vs-C++ performance delta is noise-level: the hot loops are linear scans over primitive arrays, the pattern where bounds checks are hoisted or eliminated by iterators and where `&mut` no-alias information is at least as good as C `restrict`. The NADER worst case (7.7%) is an upper bound for index-heavy code, not for iterator-style columnar loops.
- Borrow-checker friction with graph structures is real for pointer-linked nodes but largely disappears with the representation this engine wants anyway (nodes and edges as `u32` indices into flat arrays/CSR). That choice is also what makes the layout cache-friendly and serialisable.
- The FFI-bool miscompilation in 1.99.0 is a direct relevance flag for a C-ABI library: pin the toolchain, and include cross-language golden tests in CI.

### Gaps
- No session-verified head-to-head numeric benchmark of Rust vs C/C++ for simulation kernels (e.g. Benchmarks Game, Rapier vs PhysX/Bullet/Jolt figures, krABMaga vs MASON numbers from the 2022 paper) was retrieved.
- Unverified recollection: Google reported about 0.30% average performance cost from enabling hardened libc++ bounds checks fleet-wide (security.googleblog.com, Nov 2024) — relevant as evidence that bounds checking in C++ is equally cheap; page unreachable in this session.
- Veloren and Ruffle status in 2026 were not researched (search budget exhausted). Rust aliasing-optimisation benchmarks (noalias) were not retrieved.

## 3. Data-oriented design for both workloads (SoA, columnar, ECS types, graph representation)

### Takeaway
For 10^5–10^7 homogeneous records, plain struct-of-arrays/columnar tables with hand-written passes are the simplest structure that reaches the hardware limit; published ECS benchmarks show full ECS frameworks spend about 3–8 ns per entity per system on trivial systems, and an archetype ECS beats a conventional ABM framework by up to 6x, but the ECS machinery (archetype moves, queries, scheduling) buys little when every agent has the same columns. The node graph should be flat index-based arrays (CSR), evaluated in a precomputed topological/level order with cycles broken by one-step delays.

### Cited Findings
- ECS benchmark (C++; Linux 6.10, 12-core 3.13 GHz, GCC 14.2.1; EnTT 3.13.2, flecs 4.0.1, gaia-ecs 0.8.6, mustache 0.2, pico_ecs 2.3), single-threaded "update systems" times:
  - ~1M entities, 2 systems: EnTT 12 ms, flecs 12 ms, Ginseng 10 ms, mustache 8 ms, pico_ecs 12 ms, gaia-ecs 12 ms, EntityX 21 ms
  - ~2M entities, 2 systems: EnTT 25 ms, flecs 25 ms, mustache 15 ms
  - ~1M entities, 7 systems: EnTT 57 ms (groups 51 ms, runtime views 122 ms), flecs 25 ms, mustache 21 ms, pico_ecs 31 ms, gaia-ecs 43 ms
  - ~2M entities, 7 systems: EnTT 112 ms, flecs 52 ms, mustache 42 ms
  — [abeimler/ecs_benchmark](https://github.com/abeimler/ecs_benchmark)
- EnTT's author warns that many ECS benchmarks are flawed and points to the above as the most current comparison — [skypjack/entt](https://github.com/skypjack/entt)
- Bevy ECS offers two storages chosen per component: Tables ("fast and cache friendly iteration, but slower adding and removing of components", the default) and Sparse Sets ("fast adding and removing of components, but slower iteration"); it tracks all component/resource changes, has a parallel executor that runs non-conflicting systems concurrently, and "can easily be used as a standalone crate" — [bevy_ecs README](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md)
- flecs uses "cache friendly archetype/SoA storage", supports entity relationships and a query language, and "processes millions of entities every frame" — [flecs](https://github.com/SanderMertens/flecs)
- ECS applied to agent-based models: Ark.jl (an archetype-based ECS for Julia with batch operations and per-component storage modes) runs standard ABM benchmarks in 0.36x/0.17x (Wolf-Sheep small/large), 0.74x/0.36x (Flocking) and 0.85x/0.99x (Schelling) of Agents.jl's time, at 2–3x the lines of code (e.g. 149 vs 73 for Wolf-Sheep) — [ABMFrameworksComparison](https://github.com/JuliaDynamics/ABMFrameworksComparison), [Ark.jl](https://github.com/ark-ecs/Ark.jl)
- Columnar engines as the model: Polars is built on the Apache Arrow columnar format with multi-threaded, vectorised (SIMD) execution — [pola-rs/polars](https://github.com/pola-rs/polars)
- Memory-bound character of flat-array kernels: SpMV is "O(nnz) memory bandwidth-bound", with typical per-core throughput of 5–15 GB/s on DDR4/DDR5 machines — [CPU SpMV implementations guide](https://andreolli-davide.github.io/gpu-spmv/cpu/spmv.html)

### Inferences
- Per-entity cost implied by the ECS benchmark: 1M entities x 7 systems in 21–57 ms = 3.0–8.1 ns per entity per system (flecs 25 ms → 3.6 ns; EnTT 57 ms → 8.1 ns); 2 systems in 8–12 ms = 4–6 ns. A hand-written SoA loop doing comparable arithmetic on contiguous `f32/f64` columns has no per-entity indirection and can autovectorise, so it should sit at or below the low end of that range (this is an expectation, not a measured figure).
- Archetype ECS vs sparse-set ECS vs plain columns for PoliSim: archetype storage is itself "tables of columns", so for a population in which every record has the same fields an archetype ECS degenerates to one table and adds only overhead and API surface. An ECS earns its keep when entities are heterogeneous and gain/lose components at run time (firms, parties, households of different kinds with optional state). A pragmatic split: plain columnar tables (one per record type) + hand-written systems for the population; no ECS for the node graph.
- Sparse-set ECS (EnTT's model, as conventionally described) favours cheap add/remove and single-component iteration; multi-component joins over 10^6 rows pay extra indirection (EnTT 57 ms vs flecs 25 ms at 7 systems is consistent with that), so if an ECS is used for the population, an archetype/table one fits better.
- Hot/cold splitting follows from the bandwidth numbers: at 5–15 GB/s per core, a pass over 10^7 records touching 64 bytes each (640 MB) costs about 43–128 ms just to stream memory; touching 8 bytes each (80 MB) costs about 5–16 ms. Keep per-step fields in dense narrow columns (f32, u8/u16 codes), keep identifiers/history/strings elsewhere, and fuse rule passes so each column is streamed once per step.
- Graph representation: store nodes as dense arrays (value, next value, parameters) and edges in CSR/adjacency arrays sorted by target, with `u32` indices. Compute strongly connected components once at load; any edge inside a cycle must carry a delay of at least one step (reads last step's value), which turns the per-step evaluation graph into a DAG. Topologically sort the DAG into levels; nodes in one level have no mutual dependencies and can be evaluated in parallel, levels run in sequence. Because every node writes only its own slot and reads slots from earlier levels or the previous step, results are independent of thread scheduling. For a pure double-buffered formulation (all edges read previous step), no ordering is needed at all and the whole graph is one parallel loop/SpMV.
- Cohort cells vs individuals: 10^5 cohort cells with weights are 100x cheaper than 10^7 individuals and fit in L2/L3 cache (10^5 x 64 B = 6.4 MB); the columnar layout is identical, so the engine can support both with a weight column.

- No session source was retrieved for level scheduling/topological parallel evaluation (the description above is standard algorithmic reasoning, not a citation), nor conference talks (CppCon/Handmade/GDC) on data-oriented design.

## 4. Evaluating user-defined equations fast (interpreters, bytecode, closures, Lua, Wasm, JIT) and what comparable systems do

### Takeaway
Compiled-AST/bytecode expression evaluators in Rust evaluate small formulas in roughly 0.15–0.6 µs each, about 10–20x faster than general scripting-style evaluators (3–7 µs), which is fast enough for the node graph at every size in scope without a JIT; the population workload should not run user expressions per record through a scalar interpreter but through vectorised (column-at-a-time) evaluation or ahead-of-time compilation. Established system-dynamics tools take the transpile-to-C/Wasm or compile-to-bytecode route, and Wasm (wasmtime/wasmi) is the option that gives sandboxed, deterministic mods.

### Cited Findings
- Rust expression crates, exmex-benchmarks (Exmex 0.20.5 vs Evalexpr 12.0.2, MacBook Pro M1 Max, mean evaluation time in microseconds): `sin(x)+sin(y)+sin(z)` exmex 0.16 vs evalexpr 3.26; `x^2+y*y+z^z` 0.19 vs 2.73; `x*0.02*sin(-(3*(2*sin(x-1/(sin(y*5)+(5.0-1/z))))))` 0.56 vs 6.6; a longer mixed expression 0.31 vs 9.43; exmex with dynamically typed `Val` is 0.56–1.27. Exmex parses more slowly than the others; earlier versions of the benchmark found meval and fasteval "significantly faster than Evalexpr" — [exmex-benchmarks](https://github.com/bertiqwerty/exmex-benchmarks)
- mexe's author reports it is about 4–10x faster than meval and about 2x faster than fasteval, with evalexpr generally slowest (noting those crates do more) — [mexe README](https://rust-digger.code-maven.com/src/mexe-0.2.0/README.md)
- fasteval's published benchmark data dates from December 2019 (crate 0.2.4) and claims fastest times in interpreted, compiled and unsafe-variable modes; a maintained fork exists as fasteval3 3.0.1 — [likebike/fasteval](https://github.com/likebike/fasteval), [fasteval3](https://docs.rs/crate/fasteval3/latest)
- Lua: mlua (0.12) binds Lua 5.1–5.5, LuaJIT and Luau; sandbox mode exists only for Luau; Lua 5.1–5.5 and Luau build for wasm32; the maintainers caution it contains a large amount of `unsafe` — [mlua](https://github.com/mlua-rs/mlua). LuaJIT-vs-C results vary widely: 6% slower on one numeric algorithm, about 3x slower in a 2016 comparison, 17 ns vs 7 ns per FFI iteration on an M1, and 26 ms vs 1.5 ms (17x) in a game developer's realistic vector-math test — [lua-l 2011](https://lua-users.org/lists/lua-l/2011-08/msg00804.html), [2016 comparison](https://eklausmeier.goip.de/blog/2016/04-05-performance-comparison-c-vs-lua-vs-luajit-vs-java), [bun-c-luajit-bench](https://github.com/funatsufumiya/bun-c-luajit-bench), [giraffe wiki](https://github.com/hsjunnesson/giraffe/wiki)
- WebAssembly runtimes: Wasmtime documents the sources of Wasm non-determinism and how to remove them — do not expose non-deterministic host imports; NaN bit patterns are unspecified, fixed by `cranelift_nan_canonicalization` at some floating-point cost; relaxed SIMD "gave up determinism across different architectures", fixed by `relaxed_simd_deterministic` or by disabling the proposal; `memory.grow` may non-deterministically fail; use fuel-based rather than epoch-based interruption — [Wasmtime deterministic execution doc](https://github.com/bytecodealliance/wasmtime/blob/main/docs/examples-deterministic-wasm-execution.md)
- wasmi is "an efficient, lightweight, and deterministic WebAssembly interpreter", `no_std`, with built-in fuel metering, SIMD (0.43) and relaxed-SIMD (0.44) support, two security audits, and Apache-2.0/MIT licensing — [wasmi](https://github.com/wasmi-labs/wasmi)
- Cranelift vs LLVM code quality: in a 2020 comparison discussed by Bytecode Alliance developers, Wasmtime/Cranelift trailed V8 TurboFan by a few percent and LLVM-based WAVM by roughly 10% while compiling about 10x faster; maintainers describe Cranelift as less optimised than LLVM but capturing most of the performance, and 2026 user reports show pathological gaps (20–31x) on code that relies on inlining Cranelift does not perform; Wasmer moved to LLVM for production "closer to native" performance — [Bytecode Alliance Zulip: Cranelift vs LLVM](https://bytecodealliance.github.io/zulip-archive/stream/217117-cranelift/topic/Comparisons.20between.20cranelift.20and.20LLVM.3F.html), [Zulip: is Cranelift an optimizing backend?](https://bytecodealliance.github.io/zulip-archive/stream/217117-cranelift/topic/Does.20cranelift.20aim.20to.20be.20optimizing.20compiler.20backend.3F.html), [Wasmer 6 announcement](https://wasmer.io/posts/announcing-wasmer-6-closer-to-native-speeds), [LWN on Cranelift](https://lwn.net/Articles/964735)
- Comparable systems:
  - SDEverywhere transpiles Vensim or Stella models to C, JavaScript or WebAssembly; in production since 2019 for Climate Interactive's En-ROADS and C-ROADS and Energy Innovation's Energy Policy Simulator; handles "complex models with thousands of equations"; Euler integration only; MIT — [SDEverywhere](https://github.com/climateinteractive/SDEverywhere)
  - Simlin is an open-source system-dynamics tool (Apache-2.0) whose simulation engine is written in Rust and compiled to WebAssembly for the browser; `pysimlin` loads XMILE, Vensim MDL and protobuf models and returns pandas DataFrames — [bpowers/simlin](https://github.com/bpowers/simlin), [pysimlin](https://pypi.org/project/pysimlin/0.1.3/)
  - BPTK-Py added an XMILE compiler and a Rust back-end described as giving "significantly faster simulation performance" (vendor claim, no numbers) — [bptk-py](https://pypi.org/project/bptk-py/)
  - ModelingToolkit.jl symbolically preprocesses equation systems (e.g. automatic index reduction via `@mtkcompile`) and generates fast functions including Jacobians/Hessians, with automatic sparsification and parallelisation — [ModelingToolkit.jl](https://github.com/SciML/ModelingToolkit.jl)
  - SuiteSparse:GraphBLAS JIT-compiles the kernels it needs at run time and caches them on disk (`~/.SuiteSparse`) — [GraphBLAS](https://github.com/DrTimothyAldenDavis/GraphBLAS)
  - Factorio runs gameplay mods in Lua inside a deterministic lockstep simulation; a 2024 Friday Facts post describes a cross-machine (Windows/Linux) desync traced to the modding API — [Factorio FFF-415](https://direct.factorio.com/blog/post/fff-415)
  - FLAME GPU 2 compiles agent functions either ahead of time or at run time (C++ "RTC"), and transpiles Python agent functions to C++ (experimental) — [FLAMEGPU2](https://github.com/FLAMEGPU/FLAMEGPU2)

### Inferences
- Node-graph budget with a compiled-AST evaluator (0.16–0.56 µs per expression, exmex on an M1 Max): 300 nodes → 48–170 µs per step; 3,000 nodes → 0.5–1.7 ms; 30,000 nodes → 4.8–17 ms, single-threaded. With an evalexpr-class evaluator (2.7–9.4 µs): 300 nodes → 0.8–2.8 ms; 30,000 nodes → 80–280 ms. So evaluator choice is irrelevant for a Democracy-3-sized graph and decisive only at tens of thousands of nodes or when thousands of steps are run for AI look-ahead/Monte Carlo (e.g. 10,000 steps x 30,000 nodes x 0.3 µs ≈ 90 s).
- Population workload: a scalar interpreter at about 0.2 µs per expression over 10^7 records is 2 s per expression per step — too slow. The standard remedy is the dataframe-engine approach: interpret the expression once per step over whole columns (each opcode is a tight native loop over a batch of, say, 1,024–4,096 values), which amortises dispatch to well under 1 ns per record per opcode and keeps SIMD. This needs no JIT and therefore works on platforms that forbid run-time code generation.
- Options ranked by (speed, determinism, platform reach) for this project:
  1. Parse → typed expression DAG → constant-fold/common-subexpression-eliminate → flat register bytecode, with a scalar path (graph) and a batched/column path (population). Deterministic by construction if the opcode set uses only correctly-rounded basic ops plus a pinned math library; runs everywhere including wasm, consoles and iOS.
  2. Ahead-of-time code generation (emit Rust/C from the model definition at build time, as SDEverywhere does). Fastest and fully deterministic, but mods then need a compiler toolchain or fall back to option 1.
  3. Wasm mods (wasmtime with Cranelift on desktop; wasmi interpreter where JIT is not allowed). Sandboxed, deterministic with NaN canonicalisation and without relaxed SIMD/threads; expect roughly 10% or more below LLVM-native on desktop and interpreter-level speed under wasmi.
  4. LuaJIT/Luau via mlua: most familiar to modders, but only Luau has a sandbox mode, LuaJIT's speed advantage disappears where JIT is forbidden, and float/trig determinism across platforms becomes the embedder's problem (cf. Factorio's mod-API desync).
  5. In-process JIT with Cranelift or LLVM (inkwell): highest ceiling, largest dependency and platform burden; not needed given the numbers above.
- A dependency-light design is to make option 1 the canonical semantics and treat options 2/3 as accelerators that must reproduce its results bit-for-bit (testable by replay hashes).

## 5. Graph and sparse linear algebra options; is a few-hundred-node graph ever a performance problem?

### Takeaway
No: a few-hundred-node graph costs microseconds per step as a sparse matrix-vector product and well under a millisecond even through an expression interpreter; even 10^6 edges is about 1–4 ms on one core. A sparse-linear-algebra library is therefore unnecessary for the graph at these sizes — a hand-written CSR kernel is a dozen lines — and libraries like SuiteSparse:GraphBLAS only make sense if the design later needs graph algorithms at scale.

### Cited Findings
- SpMV throughput is conventionally reported as 2 x nnz / runtime (GFLOPS) and is memory-bandwidth-bound; typical per-core memory throughput is 5–15 GB/s on DDR4/DDR5 machines — [CPU SpMV implementations guide](https://andreolli-davide.github.io/gpu-spmv/cpu/spmv.html)
- A 2025 study of matrix reordering measured multi-threaded SpMV at 108 GFLOPS with a good ordering versus 32 GFLOPS with a poor one on a 64-core machine, and also tested consumer desktops such as an 8-core Intel Core i7-11700KF — [arXiv 2506.10356](https://arxiv.org/html/2506.10356v2)
- SuiteSparse:GraphBLAS v10.5.2 (20 Oct 2026; C11; Apache-2.0) implements sparse matrix operations over arbitrary semirings with run-time JIT-compiled kernels and OpenMP; it is the engine inside RedisGraph and MATLAB's sparse multiply since R2021a (up to 30x faster `C=A*B` on a 20-core machine); caveats: slow to compile (some files take minutes), performance suffers without OpenMP, not tuned for NUMA, CUDA back-end "isn't ready to use yet"; LAGraph is the recommended algorithm layer — [GraphBLAS repo](https://github.com/DrTimothyAldenDavis/GraphBLAS)
- Order-of-evaluation matters for sparse kernels: the same study shows a 3.4x swing (32 → 108 GFLOPS) purely from row/column ordering — [arXiv 2506.10356](https://arxiv.org/html/2506.10356v2)

### Inferences
- Per-core SpMV rate implied by the cited figures: 108 GFLOPS / 64 cores = 1.69 GFLOPS per core = 0.84 x 10^9 non-zeros/s; 32 GFLOPS / 64 = 0.5 GFLOPS per core = 0.25 x 10^9 non-zeros/s. Cross-check from bandwidth: CSR costs about 12 bytes per non-zero (8-byte value + 4-byte column index), so 10 GB/s gives about 0.8 x 10^9 non-zeros/s. Use 0.25–0.85 x 10^9 edges/s per core as the planning range for out-of-cache matrices.
- Step cost for a linear (weighted-sum) graph on one core: 10^4 edges → 12–40 µs; 10^5 edges → 0.12–0.4 ms; 10^6 edges → 1.2–4 ms. Small graphs fit in cache (10^4 edges x 12 B = 120 kB, inside L2) and will be at the fast end or better.
- A Democracy-3-scale graph (a few hundred nodes, a few thousand links) is about 3,000 edges → roughly 4–12 µs per step as SpMV, or 300 nodes x 0.16–0.56 µs ≈ 50–170 µs through a compiled expression evaluator (Section 4). Even 100,000 simulated steps (deep AI search or Monte Carlo) is 0.4–17 s single-threaded. The graph is never the bottleneck at this size; engineering effort belongs in the population workload and in determinism/tooling.
- When is the graph "an SpMV" versus "a general expression graph"? If each node is `f_i(sum_j w_ij * x_j(t - d_ij))` with a per-node activation/clamp, the step is SpMV plus an elementwise map, with delays handled by ring buffers per distinct delay (or one CSR matrix per delay). Democracy-style links with per-link curve equations are `sum_j g_ij(x_j)`: still a CSR traversal, with a per-edge function selector (a small enum of curve types evaluated in a `match`/switch is faster than a general expression per edge). Only arbitrary user formulas referencing many variables need the general expression path.
- Library fit: GraphBLAS is overkill and a heavy build dependency for a consumer game (minutes-long compiles, OpenMP, run-time C-compiler JIT cache); petgraph-style adjacency structures are convenient for load-time analysis (SCC, toposort), then lower to flat CSR arrays for run time.

### Gaps
- Current versions/maintenance status and benchmark data for sprs, faer (sparse), nalgebra-sparse, Eigen sparse, petgraph and LAGraph were not retrieved.
- Per-core SpMV figures specifically for consumer desktop CPUs in arXiv 2506.10356 were not extracted; the per-core rates above are derived by dividing 64-core totals and are approximate (multi-core scaling of a bandwidth-bound kernel is sublinear, so single-core rates may be higher than total/64).

## 6. Parallelism: work-stealing vs fixed partitioning, SIMD, memory bandwidth, published throughput figures

### Takeaway
Published figures put tuned columnar scan-and-aggregate code at roughly 80–100 million records per second per core, and ECS-style per-entity rule passes at 120–330 million entity-updates per second per core, so 10^6 records with a few dozen rules is a 10–100 ms single-threaded step and 10^7 records needs multi-core plus attention to memory bandwidth. Deterministic parallelism is achievable (Rapier and Box2D both ship it) by fixed, data-defined partitioning of work and order-fixed reductions rather than by depending on scheduler behaviour.

### Cited Findings
- One Billion Row Challenge (parse text + per-key min/mean/max over 10^9 rows; Hetzner AX161, AMD EPYC 7502P Zen 2): best official result 1.535 s on 8 cores; best result on all 32 cores/64 threads 0.323 s; naive single-threaded baseline 4 min 49.7 s — [gunnarmorling/1brc](https://github.com/gunnarmorling/1brc)
- ECS update benchmark, single thread: ~1M entities x 7 systems in 21 ms (mustache), 25 ms (flecs), 57 ms (EnTT); ~2M x 7 in 42–112 ms — [abeimler/ecs_benchmark](https://github.com/abeimler/ecs_benchmark)
- SIMD: Highway's maintainers report "often 5-10x speedups" from explicit SIMD, describe explicit vector code as "more predictable and robust to code changes/compiler updates than autovectorization", and warn that SIMD code that fails to inline "may slow down by factors of 10 to 100" — [google/highway](https://github.com/google/highway). A Rust SIMD survey likewise concludes autovectorisation "remains unreliable" — [Shnatsel survey](https://shnatsel.medium.com/the-state-of-simd-in-rust-in-2025-32c263e5f53d)
- Deterministic parallel execution exists in shipping libraries: Rapier's `parallel` feature gives results that match sequential regardless of thread count, but its cross-platform `enhanced-determinism` feature cannot be combined with the `simd` features (SIMD lane width forms a separate determinism domain) — [Rapier determinism docs (search summary)](https://rapier.rs/docs/user_guides/rust/determinism). Box2D v3 (C17) combines multithreading, SIMD and cross-platform determinism — [erincatto/box2d](https://github.com/erincatto/box2d)
- Memory bandwidth: typical 5–15 GB/s per core on DDR4/DDR5 systems — [CPU SpMV implementations guide](https://andreolli-davide.github.io/gpu-spmv/cpu/spmv.html)
- Dataframe engines: Polars reported PDS-H (TPC-H-derived, not audited) results in July 2026 averaging 6.4x faster than Spark on a single 128-vCPU node; DuckDB published a v2.0-dev TPC-H SF1000 benchmark on 16 Oct 2026 — [Polars July 2026 post](https://pola.rs/posts/polars-in-aggregate-jul26), [DuckDB Oct 2026 post](https://duckdb.org/2026/10/16/nvidia-vera-benchmark). A low-rigour blog comparison reports a 10-million-row aggregation in 0.61 s (Polars 1.12) and 0.43 s (DuckDB 1.3) using several threads — [dev.to comparison](https://dev.to/gowthampotureddi/polars-vs-pandas-vs-duckdb-benchmarked-speed-memory-api-trade-offs-40op)
- Tax-benefit microsimulation: PolicyEngine's stack (built on an OpenFisca-derived core) is vectorised Python that "can process thousands of households simultaneously"; no throughput figure is published in the sources found — [policyengine-taxsim](https://pypi.org/project/policyengine-taxsim/), [PolicyEngine GitHub](https://www.github.com/PolicyEngine)
- Threaded wasm in the browser needs SharedArrayBuffer and cross-origin isolation, nightly Rust and a rebuilt std — [wasm-bindgen-rayon](https://github.com/RReverser/wasm-bindgen-rayon)

### Inferences
- Throughput arithmetic from 1BRC: 10^9 rows / 1.535 s / 8 cores = 81 x 10^6 rows/s per core; 10^9 / 0.323 s / 32 cores = 97 x 10^6 rows/s per core; naive baseline 10^9 / 289.7 s = 3.5 x 10^6 rows/s. These include text parsing and hashing, so a binary columnar group-by (cohort index already an integer column) should be faster. Aggregating 10^7 agents back into graph nodes at about 10^8 rows/s per core is about 0.1 s on one core, about 15–20 ms on 8.
- Throughput arithmetic from the ECS benchmark: 7 x 10^6 entity-updates in 21–57 ms = 123–333 x 10^6 entity-system updates/s per core. For 10^6 agents and 30 rule passes: 30 x 10^6 updates → 90–245 ms single-threaded; with 8 cores at about 6x effective scaling, 15–40 ms. For 10^7 agents: 0.9–2.4 s single-threaded, 0.15–0.4 s on 8 cores — acceptable for a turn-based game step, marginal for interactive scrubbing or look-ahead search, which argues for cohort aggregation (10^5 cells) as the default and individuals as an option.
- Bandwidth ceiling: 10^7 records x 64 B = 640 MB per full pass; dual-channel consumer DDR5 does not scale per-core bandwidth linearly, so beyond roughly 4–6 threads a streaming pass over cold data stops speeding up. Mitigations: narrow hot columns, fused passes, and processing in cache-sized blocks (e.g. 4,096 records) through all rules before moving on.
- SIMD expectation: per-agent rule evaluation that is branch-light arithmetic over f32 columns can gain about 4–8x from AVX2 (8 lanes) and 2–4x from NEON (4 lanes) when written as explicit SIMD or reliably autovectorised; rule sets dominated by table look-ups, branches and random draws gain far less. Treat the Highway "5-10x" as an upper band for ideal kernels.
- Work-stealing (rayon, TBB) vs fixed partitioning: for uniform per-record work, static chunking by index range gives the same speed as work-stealing and makes the mapping of records to chunks independent of the scheduler; that property is what allows per-chunk partial sums to be combined in fixed chunk order for bit-identical results at any thread count. Work-stealing remains fine for execution as long as chunk boundaries and combination order are fixed by data, not by which thread ran what.
- False sharing: per-thread accumulators must be cache-line padded or kept on each worker's stack and merged afterwards; writing per-record outputs into disjoint index ranges of a shared column is safe when chunks are much larger than a cache line.
- NUMA is not a design concern on consumer PCs (single socket); P-core/E-core heterogeneity is, and favours dynamic chunk claiming over one-chunk-per-thread.
- Browser builds should assume single-threaded wasm as the baseline (threads require nightly Rust and site-level headers), which is another reason to size the default population (cohorts) so one core suffices.

### Gaps
- No published records-per-second figures were found for tax microsimulation engines (PolicyEngine, OpenFisca, EUROMOD, TAXSIM, Tax-Calculator) or for single-threaded DuckDB/Polars scans; the search budget was exhausted before these could be pursued.
- rayon's current version/features, OpenMP and oneTBB/Taskflow specifics, and any direct AVX2/AVX-512/NEON speed-up measurements on agent-rule kernels were not retrieved; the SIMD gains above are expectations.
- AVX-512 availability on current consumer CPUs (Intel client parts vs AMD Zen 4/5) and AVX10 status were not verified.

## 7. Determinism: where divergence comes from, how each language controls it, and what lockstep games do

### Takeaway
IEEE-754 basic operations (+, −, ×, ÷, sqrt, fused multiply-add when requested explicitly) are bit-reproducible across compliant hardware; cross-machine divergence comes from everything around them — libm transcendental functions, compiler-introduced FMA contraction/fast-math/reassociation, SIMD-width-dependent reduction order, thread-dependent reduction order, NaN payloads, and unordered containers. Rust gives the strictest defaults of the four languages (no contraction, no fast-math, specified float semantics), C/C++ can match with flags, and shipping engines (Rapier, Box2D v3, Factorio) show that float-based cross-platform determinism is practical if math functions are owned and ordering is fixed.

### Cited Findings
- Rust guarantees (RFC 3514): `+ - * / %`, `abs`, `copysign`, `mul_add`, `sqrt`, float casts and comparisons exactly match IEEE 754-2008 with round-to-nearest-even; NaN sign/payload are non-deterministic; 32-bit x86 is a known exception (x87 return registers alter NaN payloads, and i586 computes with different internal precision); Rust does not support changing rounding mode; strict IEEE semantics preclude contracting `a*b + c` into FMA; fast-math would require separate opt-in intrinsics/types. The RFC does not give guarantees for transcendental functions — [RFC 3514](https://github.com/rust-lang/rfcs/blob/master/text/3514-float-semantics.md)
- Rust forum guidance: rustc does not fuse `x*y+z` into FMA by default; std's transcendental functions defer to the platform libm and so are not guaranteed identical across platforms; using the pure-Rust `libm` implementations instead of std methods is "necessary and sufficient" for enhanced determinism — [users.rust-lang.org thread on deterministic floats](https://users.rust-lang.org/t/on-getting-floating-points-deterministic/142232), [older thread](https://users.rust-lang.org/t/floating-point-does-same-formula-with-same-inputs-give-same-result/100398)
- The `libm` crate is a port of musl's libm to Rust usable in `no_std`; its repository was archived on 28 April 2025 after being merged into `compiler-builtins`, where development continues — [rust-lang/libm](https://github.com/rust-lang/libm)
- Rapier: locally deterministic by default (same machine, same Rapier version, same compiler); cross-platform determinism requires the `enhanced-determinism` feature, which cannot be combined with `simd` features; `parallel` results match sequential for any thread count; trig and other non-basic functions in user code must go through nalgebra's `ComplexField`/`RealField` rather than std float methods; the JS/Wasm build is fully cross-platform deterministic; snapshot hashes (MD5) are the suggested verification — [Rapier determinism docs (search summary)](https://rapier.rs/docs/user_guides/rust/determinism), [JS docs](https://rapier.rs/docs/user_guides/javascript/determinism). Godot's "cross-platform deterministic" Rapier builds are explicitly the slower builds without SIMD and parallel solving — [Godot asset library entry](https://godotengine.org/asset-library/asset/edit/13099)
- Box2D v3 (C17) lists cross-platform determinism together with multithreading and SIMD — [erincatto/box2d](https://github.com/erincatto/box2d)
- Factorio: desyncs are detected by comparing CRC checksums of game state between peers; developers report building with strict floating-point settings on GCC and Visual Studio, that the few cross-platform float issues they saw came from differing implementations of math functions such as `sin` rather than basic arithmetic, and that fixed point is used in a few places but is impractical for most things; a 2024 post documents a real Windows/Linux desync involving the modding API — [FFF-47 "CRC fun"](https://direct.factorio.com/blog/post/fff-47), [FFF-108 forum reply](https://forums.factorio.com/viewtopic.php?p=113656), [developer AMA reply](https://axebps-redlib.hf.space/r/factorio/comments/in5d3i/developer_technicaloriented_ama/g45axjw), [FFF-415](https://direct.factorio.com/blog/post/fff-415)
- Correctly rounded math: the CORE-MATH project provides correctly rounded elementary functions intended for integration into glibc, musl, LLVM libc and others; glibc has been replacing functions with CORE-MATH versions since late 2024 (e.g. `tanhf`, `tanpif`, `tanf`), described as correctly rounded in any rounding mode and sometimes faster than the previous generic code; the rationale given is that correct rounding yields results reproducible across hardware, compiler and OS; LLVM libc makes the same argument; a Rust `core-math` crate exists — [CORE-MATH overview](https://reliable-computing.org/correctrounding.html), [libc-alpha proposal](https://sourceware.org/pipermail/libc-alpha/2022-January/134875.html), [LLVM libc math](https://libc.llvm.org/math), [core-math crate](https://docs.rs/core-math), [Zimmermann accuracy comparison incl. glibc 2.42](https://homepages.loria.fr/PZimmermann/papers/glibc242.pdf)
- FMA hazard illustrated: a fused multiply-add rounds once on FMA hardware and twice elsewhere, which breaks bit-equality unless contraction is controlled — [alice-det-math docs](https://docs.rs/alice-det-math)
- WebAssembly: NaN bit patterns are the main non-determinism in core Wasm floats; relaxed SIMD deliberately gives up cross-architecture determinism; Wasm 3.0 defines a deterministic profile; Wasmtime exposes switches for NaN canonicalisation and deterministic relaxed SIMD — [Wasmtime doc](https://github.com/bytecodealliance/wasmtime/blob/main/docs/examples-deterministic-wasm-execution.md), [Wasm 3.0 announcement](https://webassembly.org/news/2025-09-17-wasm-3.0/)
- Counter-based RNGs: Random123 (C/C++/CUDA headers) provides Philox, Threefry, ARS and AESNI as stateless functions of (counter, key) that pass TestU01 SmallCrush, Crush and BigCrush, cost a few cycles per byte, and are "easier to parallelize" than conventional generators — [Random123](https://github.com/DEShawResearch/random123). Rust crates: `squares` (`no_std` Squares CBRNG; 2^64 outputs per key; README claims about 2x Philox speed; keys must satisfy quality restrictions) and `urng` (Philox 4x32/2x64, Threefry 2x32/4x32, Squares) — [squares](https://docs.rs/crate/squares/0.1.0/source/README.md), [urng](https://docs.rs/crate/urng/0.13.0). FLAME GPU 2's default GPU random engine is Philox — [FLAMEGPU2](https://github.com/FLAMEGPU/FLAMEGPU2)
- GPU shading languages are looser: WGSL's floating-point evaluation rules permit reassociation and fusion and do not fix a single rounding behaviour for all evaluation — [luma.gl GPU precision notes](https://luma.gl/docs/api-guide/shaders/gpu-floating-point-precision), [WGSL spec](https://www.w3.org/TR/wgsl/)

### Inferences
- Divergence sources and controls, by language:
  - Transcendentals (`exp`, `ln`, `pow`, `sin`, `tanh`, …): never call the platform libm on any language. Ship one implementation in-tree: Rust `libm`/`core-math` crates; C/C++/Zig a vendored musl-derived or CORE-MATH source. Correctly rounded functions (CORE-MATH) are the strongest choice because the result is defined mathematically rather than by one code base. Alternatively restrict the model language to +, −, ×, ÷, sqrt, min/max, clamps and piecewise-linear/table curves, which are IEEE-exact.
  - FMA contraction: Rust never contracts implicitly; C/C++ need `-ffp-contract=off` (GCC contracts by default in GNU modes; Clang's default has changed across versions) and MSVC `/fp:precise` or `/fp:strict`; Zig's default float mode is strict with opt-in optimised mode per scope (compiler-flag specifics not re-verified this session).
  - Fast-math/reassociation: forbidden everywhere in the sim core (`-ffast-math`, `/fp:fast`, Zig optimised float mode, Rust "algebraic"/fast intrinsics).
  - x87: only relevant if 32-bit x86 is a target; do not ship one.
  - SIMD: elementwise SIMD is bit-identical to scalar for IEEE basic ops; reductions are not unless the summation tree is fixed. Define reductions as "8 (or 16) interleaved lanes then a fixed pairwise combine" and implement the same tree in scalar fallback, NEON and AVX2/AVX-512 code paths. Rapier's choice to exclude SIMD from its cross-platform mode is the conservative alternative.
  - Parallel reductions: partition by fixed record ranges, reduce each range sequentially (or with the fixed lane tree), combine partials in range order. Optionally accumulate monetary aggregates in integers/fixed point (e.g. i64 cents or i128), which makes sums exactly associative and order-free.
  - Hash-map iteration: never iterate an unordered map in simulation logic; use index-addressed arrays, sorted vectors, B-tree maps or insertion-ordered maps.
  - RNG: one counter-based generator keyed by (world seed, stream/purpose id) with counter = (entity id, step, draw index) gives every entity an independent, order-free, thread-free stream and makes random access/replay trivial; float conversion must be defined (e.g. top 24/53 bits → [0,1)).
  - NaN payloads: avoid making decisions or hashes depend on NaN bit patterns; canonicalise before hashing state.
- Fixed-point or integer state is a legitimate alternative for money/population counts (exact, portable, order-independent sums) with floats kept for rates/opinions; Factorio's experience suggests full fixed-point everywhere is impractical.
- Verification practice converges across Factorio and Rapier: hash (CRC/MD5) the full state every N steps, compare across peers/platforms in CI (x86-64 Windows/Linux, ARM64 macOS, wasm), and keep golden replay files. This is cheap for a headless library and should be a day-one CI job for PoliSim.
- Rust's defaults (specified semantics, no implicit contraction, no fast-math, pure-Rust libm available, wasm as a deterministic target) make "bit-identical across machines" the least effortful in Rust; C and C++ can reach the same result but rely on per-compiler flags being right on every platform and every translation unit, and on third-party libraries not having been built with fast-math.

### Gaps
- Glenn Fiedler's "Floating Point Determinism" (gafferongames.com/post/floating_point_determinism/) and Bruce Dawson's "Floating-Point Determinism" (randomascii.wordpress.com/2013/07/16/floating-point-determinism/) could not be fetched (hosts blocked); the report writer should treat them as recommended background, not as cited here.
- No primary source was retrieved for: exact current default `-ffp-contract` settings in GCC 16/Clang 21+, MSVC `/fp` behaviour, Zig's `@setFloatMode`, Rust's `HashMap` random seeding, crlibm status, or RTS-engine practice beyond Factorio (e.g. Age of Empires/StarCraft lockstep write-ups).
- Whether the Rust `libm` crate enables hardware `sqrt`/`fma` paths by default (which is still IEEE-exact) and how its results compare bit-for-bit with musl on every function was not verified.
- Squares RNG quality claims come from the crate README; independent test results were not retrieved.

## 8. GPU compute for agent populations

### Takeaway
GPU agent frameworks do deliver large populations (FLAME GPU 2 runs 10M-agent models in a fraction of a second per run on a high-end card), but they cost portability (CUDA-first; partial AMD on Linux only), licence freedom (AGPL), and cross-vendor bit-determinism (shader float rules allow reassociation and fusion). With CPU throughput of 10^8-order record-updates per second per core, a GPU back-end is not justified below about 10^7 agents for a turn-based game; keeping the CPU layout as flat columns preserves the option.

### Cited Findings
- FLAME GPU 2: "GPU accelerated agent based modelling framework for CUDA C++ and Python"; licence AGPL-3.0-only with a commercial licence available; still in a pre-release/release-candidate state; requires CUDA ≥ 12.4 (≥ 13.2 with VS 2026), a C++20 host compiler and CMake ≥ 3.25.2; NVIDIA on Linux and Windows; AMD via ROCm/HIP ≥ 7.0 on Linux only and without Python, run-time compilation, visualisation or MPI; no CPU fallback is described; default GPU RNG is Philox — [FLAMEGPU2 README](https://github.com/FLAMEGPU/FLAMEGPU2)
- The FLAME GPU 2 paper (Richmond et al., Software: Practice and Experience, 2023) benchmarks models with millions of agents, including Sugarscape at up to 16M agents — [White Rose eprint](https://eprints.whiterose.ac.uk/199416/). The Sheffield RSE group re-benchmarked on V100/A100/H100 and notes brute-force all-to-all messaging becomes costly at scale, hence specialised communication patterns — [RSE Sheffield blog](https://rse.shef.ac.uk/blog/2023-08-18-benchmarking-flamegpu2-on-h100-a100-and-v100-gpus)
- A third-party benchmark page (AMBER project; RTX 5090; methodology unverified) reports FLAME GPU 2 leading its wealth and random-walk models, with the wealth model at 28 ms for 1M agents and 226 ms for 10M agents — [AMBER benchmarks (search summary)](https://ambr.readthedocs.io/en/stable/benchmarks.html)
- wgpu: current release is v30.0.2 (12 Nov); major (breaking) releases landed as v28.0.0 (18 Dec), v29.0.0 (19 Mar) and v30.0.0 (1 Jul), i.e. roughly quarterly; MSRV bumps are treated as breaking and never exceed "stable − 3" — [wgpu releases](https://github.com/gfx-rs/wgpu/releases)
- WebGPU in browsers: Chromium since 113; Safari 26 on by default across Apple platforms; Firefox 141 enabled it on Windows (July 2025) and on Apple-silicon macOS in late 2025/January 2026 (sources differ: Firefox 145 vs 147), with Linux, Android and Intel Macs still in progress — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers), [gpuweb implementation status](https://github.com/gpuweb/gpuweb/wiki/implementation-status), [TechSpot](https://www.techspot.com/news/110456-webgpu-now-brings-desktop-quality-graphics-all-major.html)
- Determinism: WGSL evaluation rules permit reassociation and fusion of floating-point expressions and do not specify one rounding behaviour for all evaluation; `f16` depends on hardware support — [luma.gl notes](https://luma.gl/docs/api-guide/shaders/gpu-floating-point-precision), [WGSL spec](https://www.w3.org/TR/wgsl/)
- SuiteSparse:GraphBLAS's CUDA back-end is "not ready to use yet" — [GraphBLAS repo](https://github.com/DrTimothyAldenDavis/GraphBLAS)
- Work to run Rust's portable SIMD code on GPUs (VectorWare, August 2026) exists but depends on nightly `std::simd` — [CoderCops article](https://blog.codercops.com/blog/rust-portable-simd-gpu-vectorware-2026)

### Inferences
- CPU baseline for comparison (Section 6): about 1.2–3.3 x 10^8 simple entity-updates/s per core, so 10^7 agents x 30 rule passes ≈ 0.15–0.4 s on 8 cores. The AMBER figure (10M agents in 226 ms for the wealth model on an RTX 5090, steps per run unknown) shows GPUs are faster, but a turn-based political sim that advances one step per player action does not need a sub-100 ms step at 10^7 agents, and at the more likely 10^5–10^6 scale the CPU step is already 2–40 ms.
- Costs of a GPU path for this project: (1) bit-identical replays across NVIDIA/AMD/Intel/Apple GPUs are not guaranteed by WGSL/SPIR-V float rules, so GPU results could not be the authoritative simulation state unless restricted to integer arithmetic; (2) consumer-PC coverage requires wgpu/WebGPU rather than CUDA, and wgpu's quarterly breaking releases add maintenance; (3) FLAME GPU 2 is AGPL (commercial licence needed for a closed game), CUDA-centric and has no CPU fallback; (4) a second implementation of every rule (CPU reference + shader) doubles the testing surface.
- A defensible position: design the population store as flat SoA columns with rules expressed as column kernels (which is also what a compute shader needs), ship CPU-only, and revisit GPU only if profiling shows a need above about 10^7 individuals or for non-authoritative uses (visualisation, Monte Carlo ensembles for analysis where bit-exactness is not required).

### Gaps
- No verified GPU-vs-CPU speed-up ratios for rule-based population updates (as opposed to spatial ABMs) were retrieved; the AMBER page itself could not be fetched, and its number of steps per run is unknown, so per-step GPU throughput cannot be computed from it.
- Vulkan compute, CUDA-specific determinism behaviour, and integer-only shader determinism across vendors were not researched. wgpu release years are inferred from day/month on the releases page (v28 = Dec 2025, v29–v30 = 2026).

## 9. Persistence and interchange

### Takeaway
The default Rust binary serialiser of past years, bincode, was declared unmaintained in December 2025; current choices are postcard (stable, documented wire format), rkyv (zero-copy, validated), wincode (bincode-compatible) and bitcode (fastest, but format explicitly unstable). For a deterministic engine the natural design is columnar snapshots plus an input/event log, with periodic state hashes — the pattern Factorio and Rapier use for desync detection.

### Cited Findings
- bincode: RustSec advisory RUSTSEC-2025-0141 (published 16 December 2025) marks bincode unmaintained after the team ceased development; 1.3.3 is considered complete; suggested alternatives are wincode, postcard, bitcode and rkyv — [RUSTSEC-2025-0141](https://api.osv.dev/v1/vulns/RUSTSEC-2025-0141), [bincode docs page](https://docs.rs/bincode/*/)
- postcard (1.1): `no_std` + serde; "as of v1.0.0, postcard has a documented and stable wire format"; varint encoding for integers, lengths and enum discriminants; serde `flatten` and `skip_serializing_if` are unsupported and `skip` can silently break enum ordering — [postcard](https://github.com/jamesmunns/postcard)
- rkyv: zero-copy deserialisation framework; safe access API validates buffers via `bytecheck`; unchecked API for maximum speed; uses `rend` for endian-agnostic archives; recommended by the former bincode maintainers as the best option for many bincode use cases — [rkyv](https://github.com/rkyv/rkyv), [RUSTSEC-2025-0141](https://api.osv.dev/v1/vulns/RUSTSEC-2025-0141); migration experience report — [users.rust-lang.org](https://users.rust-lang.org/t/heads-up-bincode-rkyv-experiences/137359)
- bitcode: "does not attempt to have a stable format", so unsuitable for long-lived saves — [bitcode docs](https://docs.rs/crate/bitcode/0.5.1)
- wincode: Anza's serialiser designed to be wire-compatible with bincode 1.3.3 — [Anza blog](https://www.anza.xyz/blog/wincode-bincode-compatible-rust-serializer)
- Arrow: Polars uses the Apache Arrow columnar format for zero-copy data sharing with other tools — [pola-rs/polars](https://github.com/pola-rs/polars)
- State hashing: Factorio compares CRCs of game state to detect desyncs; Rapier recommends comparing hashes of serialised world snapshots across machines — [FFF-47](https://direct.factorio.com/blog/post/fff-47), [Rapier JS determinism docs](https://rapier.rs/docs/user_guides/javascript/determinism)
- pysimlin returns simulation results to Python as pandas DataFrames — [pysimlin](https://pypi.org/project/pysimlin/0.1.3/)

### Inferences
- Save design options:
  - Snapshot saves: dump the columnar state (population columns, node values, delay buffers, RNG key/step counter) with a small versioned header; compress with a general-purpose compressor. Size estimate: 10^6 agents x 64 B hot+cold = 64 MB raw; 10^5 cohort cells = 6.4 MB raw.
  - Event-sourced/replay saves: initial scenario + seed + ordered player/AI decisions; tiny files and a free regression-test corpus, but only valid while the engine is bit-deterministic and the simulation code version is identical — so replays must embed an engine/ruleset version and the engine must either keep old rule versions or fall back to the nearest snapshot.
  - Practical hybrid: event log as the canonical record, with periodic snapshots and state hashes for fast loading and divergence detection.
- Format choice: because the population is already columnar, writing columns as raw little-endian arrays (or Arrow IPC/Parquet for the analysis path) avoids a per-record serialiser entirely and gives Python/pandas/Polars/DuckDB direct access; serde + postcard is a reasonable fit for the small, structured parts (scenario definitions, graph topology, metadata) where a documented stable format matters. rkyv suits memory-mapped instant-load snapshots but ties the on-disk layout to Rust type definitions, which makes schema evolution the engine's own responsibility.
- Schema versioning: explicit version number in every file, additive column evolution (new columns get defaults; removed columns are ignored), and migration functions keyed by version; avoid formats whose layout changes with crate versions (bitcode).
- In C/C++/Zig the same design applies with hand-written column I/O or Arrow C data interface/FlatBuffers/Cap'n Proto; none of those were researched here.

### Gaps
- Arrow/Parquet crate versions, SQLite-as-save-file practice, and zstd ratios/speeds were not researched (search budget exhausted). No benchmark numbers for postcard/rkyv/bitcode were retrieved.
- rkyv's README (as fetched) does not discuss schema evolution; whether rkyv 0.8+ offers any evolution support was not verified.

## 10. Profiling and benchmarking practice

### Takeaway
All four ecosystems share the same native profilers (perf, VTune, Tracy); Rust adds well-integrated micro-benchmark harnesses (Criterion, now under a new organisation, and Divan), and the most useful practice for this project is continuous benchmarking in CI plus cross-platform state-hash tests rather than any single tool.

### Cited Findings
- Criterion.rs ("statistics-driven benchmarking library for Rust"): active development moved from `bheisler/criterion.rs` to the `criterion-rs` organisation, where maintainers are working through a PR backlog; the old repo has about 200 open issues — [bheisler/criterion.rs](https://github.com/bheisler/criterion.rs)
- Divan (0.1.21; requires Rust ≥ 1.80): attribute-based benchmarks (`#[divan::bench]`, `args = [...]`), reports fastest/slowest/median/mean, and can run each benchmark once under `cargo test --benches` as a CI smoke test — [nvzqz/divan](https://github.com/nvzqz/divan)
- Tracy: "real time, nanosecond resolution, remote telemetry, hybrid frame and sampling profiler for games and other applications"; direct support for C, C++, Lua, Python and Fortran, third-party bindings for Rust, Zig, C#, OCaml and Odin; tracks CPU zones, memory allocations, locks, context switches and GPU zones (OpenGL, Vulkan, D3D11/12, Metal, OpenCL, CUDA, WebGPU) — [wolfpld/tracy](https://github.com/wolfpld/tracy)
- Continuous benchmarking example: the Julia ABM framework comparison "is run automatically during continuous integration" with 100 seeded runs per model and medians reported — [ABMFrameworksComparison](https://github.com/JuliaDynamics/ABMFrameworksComparison)
- Benchmark hygiene warnings from practitioners: EnTT's author says many ECS benchmarks are flawed and ships an in-tree benchmark instead; the ECS benchmark suite itself calls its results "a starting point" and advises benchmarking one's own cases — [EnTT](https://github.com/skypjack/entt), [ecs_benchmark](https://github.com/abeimler/ecs_benchmark). Highway warns that non-inlined SIMD code can be 10–100x slower, a classic micro-benchmark trap — [google/highway](https://github.com/google/highway)
- Rust compiler performance is itself tracked continuously by the project (compile-time roadmap and goals) — [2026 Fast Builds roadmap](https://rust-lang.github.io/rust-project-goals/2026/roadmap-fast-builds.html)

### Inferences
- A workable practice for PoliSim regardless of language: (1) a fixed set of scenario benchmarks at three scales (300-node graph; 10^5 cohorts; 10^6–10^7 individuals) measured in steps/s and records/s per core, tracked per commit in CI on a pinned machine or with instruction-count-based measurement to cut noise; (2) Tracy zones around each system/pass for frame-style inspection from both the game client and the headless runner; (3) sampling profilers (perf/samply-style, VTune on Intel) for hot-spot and cache-miss analysis; (4) the determinism hash test from Section 7 as a required CI check on every target.
- Tool parity: C, C++ and Zig use the same perf/VTune/Tracy stack plus Google Benchmark-style harnesses; Rust's advantage is integration (`cargo bench`, Criterion/Divan), not capability.

### Gaps
- samply, cargo-flamegraph, CodSpeed/Bencher (hosted continuous benchmarking), iai-callgrind, Google Benchmark and VTune current status were not verified in this session (search budget exhausted); Divan's allocation-profiling and CodSpeed integration were not confirmed from its README.

## 11. Existing open-source engines or libraries that could be reused instead of writing from scratch

### Takeaway
Nothing found covers both workloads with the required determinism, licence and embedding properties, but several components are reusable or worth studying: Simlin (Apache-2.0, Rust, Wasm, Python) and SDEverywhere (MIT, Vensim→C/Wasm) for the system-dynamics/graph side; flecs, EnTT or bevy_ecs if an ECS is wanted; Polars/Arrow for the analysis path rather than as the live population store; and incremental-dataflow engines are a poor fit because a simulation step changes most of the state.

### Cited Findings
- System dynamics: Simlin — Apache-2.0; Rust engine compiled to WebAssembly; Python bindings (`pysimlin`) load XMILE, Vensim MDL and protobuf models; 2,525 commits and active in 2026 — [bpowers/simlin](https://github.com/bpowers/simlin), [pysimlin](https://pypi.org/project/pysimlin/0.1.3/). SDEverywhere — MIT; transpiles Vensim/Stella to C, JS or Wasm; production use since 2019 (En-ROADS, C-ROADS, Energy Policy Simulator); Euler only; no macros/strings; sketch data not converted — [SDEverywhere](https://github.com/climateinteractive/SDEverywhere). BPTK-Py has an XMILE compiler and Rust back-end — [bptk-py](https://pypi.org/project/bptk-py/). ModelingToolkit.jl is the reference for symbolic simplification and code generation of equation systems but is Julia-only — [ModelingToolkit.jl](https://github.com/SciML/ModelingToolkit.jl)
- ABM frameworks: krABMaga — MIT, Rust, MASON-style scheduler, Bevy-based visualisation (native and Wasm), MPI-distributed parameter sweeps, intra-step parallelism still "Experimental", crate 0.6.x, 228 stars — [krABMaga](https://github.com/krABMaga/krABMaga). FLAME GPU 2 — AGPL-3.0/commercial, CUDA, release-candidate state — [FLAMEGPU2](https://github.com/FLAMEGPU/FLAMEGPU2). Agents.jl is the fastest of the conventional frameworks in its own CI comparison, but Mesa (Python) is 3–159x slower and NetLogo 5–19x slower than Agents.jl, which bounds what scripting-language ABM frameworks can offer — [ABMFrameworksComparison](https://github.com/JuliaDynamics/ABMFrameworksComparison)
- ECS libraries: flecs (C99 core, MIT, archetype/SoA, relationships, query language, reflection/JSON, explorer UI, Rust/C#/Zig bindings; used in shipped games such as Tempest Rising) — [flecs](https://github.com/SanderMertens/flecs). EnTT (C++20, MIT; used by Minecraft) — [EnTT](https://github.com/skypjack/entt). bevy_ecs is usable as a standalone crate with table and sparse-set storage, change detection and a parallel scheduler; Bevy itself is at 0.20 (Oct 2026) — [bevy_ecs README](https://github.com/bevyengine/bevy/blob/main/crates/bevy_ecs/README.md), [Bevy 0.20](https://bevy.org/news/bevy-0-20/)
- Dataframe engines: Polars (MIT; Rust; Arrow memory; multi-threaded SIMD; lazy optimiser; spills to disk; Python/R/Node bindings) notes "extreme compile times" for its optimised distribution build — [pola-rs/polars](https://github.com/pola-rs/polars). DuckDB has a v2.0 development line as of October 2026 — [DuckDB blog](https://duckdb.org/2026/10/16/nvidia-vera-benchmark)
- Sparse/graph: SuiteSparse:GraphBLAS 10.5.2 (Apache-2.0) with LAGraph for algorithms — [GraphBLAS](https://github.com/DrTimothyAldenDavis/GraphBLAS)
- Incremental computation: differential dataflow (MIT, Rust, on timely dataflow) "only acts where changes in collections occur"; README example with 10M nodes/50M edges: about 15.5 s initial computation on one worker, then about 230 µs per single-edge update — "about one hundred thousand times faster than re-running the computation" — [differential-dataflow](https://github.com/TimelyDataflow/differential-dataflow)
- Tax-benefit rules: PolicyEngine publishes open-source, vectorised Python tax-benefit models (US, UK) on a core derived from OpenFisca — [PolicyEngine](https://www.github.com/PolicyEngine), [JOSS paper](https://joss.theoj.org/papers/34b9f72df98e586d7e6a2448922407e7)
- Deterministic physics libraries as architectural references (not reusable functionality): Rapier (Rust) and Box2D v3 (C) — [Rapier docs](https://rapier.rs/docs/user_guides/rust/determinism), [Box2D](https://github.com/erincatto/box2d)

### Inferences
- Reuse assessment for PoliSim:
  - Graph/system-dynamics side: Simlin's engine is the closest existing fit (Rust, permissive licence, Wasm and Python already working, reads XMILE/Vensim), and worth evaluating as a dependency or as a design reference for the equation compiler; its determinism guarantees and delay/cycle semantics would need checking against PoliSim's requirements. SDEverywhere demonstrates the ahead-of-time transpile route at production scale but brings a Node.js toolchain and Vensim as the authoring format.
  - Population side: no reusable engine matches. ABM frameworks are built around heterogeneous agents with schedulers and spatial structures, which is overhead for homogeneous tax/benefit/opinion updates; microsimulation frameworks (OpenFisca/PolicyEngine) have the right computational model (vectorised formulas over entity tables) but are Python/NumPy and country-specific. The transferable idea is their structure — variables as columns, formulas as vectorised functions with a dependency graph — which is the same "column kernel + dependency order" design reached in Sections 3–4.
  - Polars/DuckDB as the live population store: they would add a large dependency (long compile times, big binaries, fast-moving APIs), give no control over floating-point evaluation order in aggregations across versions/thread counts (a determinism risk), and are awkward in wasm. They are excellent on the analysis side: export snapshots as Arrow/Parquet and let Python users query with Polars/DuckDB.
  - ECS: only worth adopting (bevy_ecs if Rust, flecs if C, EnTT if C++) if the design grows many heterogeneous entity kinds; bevy_ecs's 0.x quarterly breaking cadence is a maintenance cost for a long-lived engine.
  - Incremental dataflow (differential dataflow, salsa-style memoisation): pays off when small input changes touch a small part of a large computation (the README's 10^5x figure is for one edge change out of 50M). A simulation step updates essentially every agent and every node, so there is little to reuse between steps. Incrementality is useful around the simulation instead: recompiling only the changed equations when a mod/scenario is edited, and "what-if" previews that recompute only the graph nodes downstream of one changed policy (a cheap topological-order partial evaluation that needs no framework).
- Writing the core from scratch is small in scope given these findings: CSR graph + level schedule, columnar tables, an expression compiler with scalar and batched evaluators, a counter-based RNG, fixed-order parallel reductions, and snapshot/replay I/O. The components above reduce risk mainly as references and test oracles (e.g. validating the equation evaluator against Simlin/PySD on standard system-dynamics test models).

### Gaps
- salsa's 2026 status, Repast HPC/Repast4Py, MASON, EnTT-based simulation engines, and timely dataflow maintenance status (Materialize's involvement) were not retrieved (search budget exhausted).
- Simlin's determinism properties, performance figures and internal design (interpreter vs bytecode VM) are not documented in its README and were not verified; PySD and Vensim performance were not researched.
- No open-source engine in the style of Democracy 3's policy/effect graph was searched for in this session (adjacent researchers may cover it).
